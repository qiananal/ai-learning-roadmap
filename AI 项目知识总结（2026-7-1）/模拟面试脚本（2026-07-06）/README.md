## 你这个投研系统里的 RAG 是怎么做的？数据从哪里来？怎么组织的？

标准回答：

我这个RAG其实更偏“结构化检索增强生成”，而不是传统的向量RAG。

我主要做了三步：

第一，数据获取阶段，我通过通达信API获取实时股价、成交量、技术指标等结构化数据。

第二，在数据组织阶段，我不会直接把自然语言拼进prompt，而是将数据统一整理成结构化JSON，例如价格、涨跌幅、均线等字段。

第三，在生成阶段，将结构化数据作为上下文输入给LLM，并通过JSON Schema约束输出格式，让模型做分析判断。

这样做的好处是避免纯文本RAG在数值分析上的误差，同时提高结果的稳定性和可控性。


### JSON Schema 是怎么减少大模型幻觉的？它在你的系统里起什么作用？

标准回答（建议你直接记这个版本）：

JSON Schema 本身并不是在模型内部起作用，而是在生成结果之后作为结构化约束进行校验。

在我的系统里，它主要起到三个作用：

第一，在输出层对模型生成结果进行结构定义，例如字段类型、范围和格式要求，避免模型输出自由文本导致结构混乱。

第二，在Function Calling或解析阶段，对模型返回结果进行强校验，如果不符合Schema，会触发重新生成或修正流程。

第三，通过这种结构化约束，可以减少模型“自由发挥”的空间，从而降低数值错误和格式错误的概率，也就是间接降低幻觉风险。

## 为什么不直接用 FastAPI + 线程池，而要用 Celery？

标准回答（建议直接背）：

我选择 Celery + Redis 的原因是它是一个典型的任务队列异步架构，而不是线程池模型。

在我的系统中，FastAPI 只负责接收请求并将任务投递到 Redis 队列中，真正的模型推理或训练任务由 Celery Worker 进程去消费执行。

这样设计的好处有三个：

第一，避免HTTP请求被长时间计算任务阻塞，提高接口响应速度；

第二，任务和执行解耦，可以横向扩展多个Worker处理高并发任务；

第三，对于像点云推理这种高耗时任务，可以独立分配计算资源，避免影响主服务稳定性。

和线程池相比，Celery是跨进程甚至跨机器的分布式方案，而线程池只适用于轻量级并发任务。


### 为什么不用 WebSocket，而选择 SSE？

标准回答：

我在这个项目中选择 SSE 而不是 WebSocket，主要是基于业务通信模式的考虑。

我的系统是一个AI分析系统，前端只需要接收后端推理过程的状态更新，比如数据处理、模型推理和最终结果输出，并不需要前端主动频繁向后端发送消息。

SSE本质是基于HTTP的单向长连接，更适合这种“后端持续推送状态、前端被动接收”的场景，实现成本更低，兼容性也更好。

而WebSocket是双向通信协议，更适合实时交互场景，比如聊天或协同编辑。在我的系统中没有强交互需求，所以使用SSE可以降低系统复杂度，同时满足实时性要求。


## langchain和langgraph的区别，以及为什么用的langgraph

LangChain 是一个面向 LLM 应用的链式开发框架，主要用于把 Prompt、工具调用、RAG、Agent 等能力串联成线性或简单流程。

LangGraph 是基于 LangChain 之上的扩展框架，它更偏向“状态机 + 图结构”，专门用来构建复杂的多Agent系统和可回溯的流程控制。

我在项目中选择 LangGraph 的原因，是因为我的应用不是单一问答或线性RAG，而是一个多步骤决策系统。

在我的投研系统中，需要多个Agent协作，包括选股分析、信号判断和持仓诊断，每一步的输出都会影响下一步决策。

这种场景本质上是一个有状态的决策流程，而不是简单的链式调用，因此 LangChain 的线性结构不够灵活。

LangGraph 提供了图结构和状态管理能力，可以让我清晰定义每个节点的输入输出，并支持条件分支和流程回溯，更适合这种多Agent决策系统。
