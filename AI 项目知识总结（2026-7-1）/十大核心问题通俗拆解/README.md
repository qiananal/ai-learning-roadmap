## 十大核心问题通俗拆解

### ① 为什么用 LangGraph？为什么不用 LangChain？

#### 一句话大白话：

“LangChain 像流水线（只能一步一步往前走），而 LangGraph 像十字路口（能倒车、能走回头路、能循环谈判）。”

#### 专业级话术：

“传统的 LangChain 采用的是链式结构（DAG，有向无环图），它的数据流是单向、线性的。但在真实的复杂多 Agent 协同场景中（比如我们投研中台的‘选股 $\rightarrow$ 风控审计 $\rightarrow$ 发现漏洞 $\rightarrow$ 退回重写’流程），我们需要循环控制流（Loops）和状态修订（State Management）。

如果强行用 LangChain 去写这种带循环判定、自主改写 Prompt 的逻辑，代码会变得极其臃肿，甚至容易陷入无限死循环。

LangGraph 的底层是一个‘带状态机的图结构（State Graph）’。它天然支持节点之间的双向循环。我们在图中定义了 State（内存保险箱），任何一个 Agent 节点在执行完后，都可以安全地将数据更新回全局 State。其他节点根据当前状态进行分支跳转（Conditional Edges），不仅完美支持了‘Agent A 起草、Agent B 审计不通过并退回’的循环谈判机制，还能轻松实现 Human-in-the-loop（人工介入确认）等高阶控制流。”

### ② RAG 怎么实现？为什么不用向量数据库？为什么用结构化 RAG？

#### 一句话大白话：

“RAG 就像带大模型做开卷考试。我们不用向量数据库，是因为向量检索是‘数学睁眼瞎’，而结构化 RAG 能保证数字精度 100% 准确。”

#### 专业级话术：

“在 AxiomFin 中，我们的 RAG（检索增强生成）流程是：‘实时拉取行情 $\rightarrow$ 规整为 Markdown 表格 $\rightarrow$ 作为 Context 注入 Prompt $\rightarrow$ 大模型诊断’。

我们为什么没有采用行业里满大街都在写的向量数据库（Vector DB）？
因为向量检索的本质是计算语义相似度，它在数学上存在‘数字钝化’的致命死穴。
例如：向量模型会将 持仓成本: 30.5 元 和 持仓成本: 30.6 元 转化为几乎完全相同的两个高维向量。进行余弦相似度计算时：

$$S_C(\vec{A}, \vec{B}) \approx 0.9999$$

在向量数据库看来，这两句话没有任何区别。但是在金融交易中，一毛钱的误差乘以 10 万股，就是整整 1 万元的真实盈亏错乱！大模型拿到被向量相似度检索错配的数据，算出来的诊断报告直接变成了废纸。此外，高频变动的秒级 K 线数据如果频繁写入向量库重建索引，会造成极高的 I/O 损耗和 CPU 锁死。

所以，我们自研了【结构化 RAG】方案：

数据从通达信 API 提取后，不进行任何向量化。直接在 Python 内存中以 float 形式计算，拼装提示词时，将数据原封不动转换为 Markdown 干净表格喂给大模型。

这种非侵入式的结构化对齐，避开了 Embedding 过程中的精度流失，实现了 $\pm0.00$ 的计算误差，并且将检索延迟压缩到了 $1\text{ms}$ 内，完全满足了高频盯盘的高精度需求。”

### ③ FastAPI 为什么异步？

#### 一句话大白话：

“传统的框架（如 Flask）来一个客人都得专门派一个服务员全程盯着他吃（一请求一线程，高并发直接卡死）；而 FastAPI 只有一个服务员，谁点完单需要等（比如等大模型 API），服务员就立刻去接待下一个人（非阻塞异步），一个人就能抗住上万并发。”

专业级话术：

“FastAPI 底层运行在基于 uvicorn 和 asyncio 的单线程事件循环（Event Loop）上，它利用了操作系统内核的 epoll（多路复用） 机制。

在传统同步框架（如 Django、Flask）中，采用的是‘一请求一线程（Thread-per-request）’。当并发用户上来时，服务器必须在内存中开辟大量物理线程。如果用户正在等待大模型 API 响应（耗时 $3 \sim 5$ 秒），这些线程就会全部处于阻塞等待状态。Linux 线程栈极耗内存，高并发下系统会迅速发生 OOM 崩溃。

而 FastAPI 通过 async/await 关键字，在发起大模型或网络 I/O 请求的一瞬间，主线程会立刻向系统注册一个监听事件，然后主动让出 CPU 控制权，转身去接待队列中的下个用户。等 3 秒后大模型接口返回数据、操作系统触发 socket 读写事件时，事件循环再重新拾起先前的协程继续执行。这种非阻塞 I/O 机制，用极低的服务器资源损耗换取了超高的系统吞吐量。”

### ④ Celery 为什么不用线程池？

#### 一句话大白话：

“线程池再怎么开，也还在同一个 Python 进程里，抢同一个 GPU。PyTorch 推理一并发，显存直接 OOM 爆红，把整个网站一起带走死机。而 Celery 是跨进程、甚至跨服务器外包，安全又防爆。”

#### 专业级话术：

“这属于**‘推理解耦与物理硬隔离’**的架构设计。

在 GAMUT 质检系统中，三维点云预处理和 DGCNN 模型推理是重度的 GPU/CPU 密集型任务（单次推理强占 $2\text{GB}$ 显存）。

如果我们在 FastAPI 内部直接开线程池（Thread Pool）并发运行 PyTorch 推理，由于所有的线程都运行在同一个 Python 进程下、共享同一块 GPU 物理内存：

首先会受到 Python GIL 锁 的致命限制，多线程计算效率直接暴跌。

更致命的是，当大并发涌入，多个线程同时向显卡申请显存时，一瞬间就会触发 CUDA out of memory。

此时，由于多线程共享进程内存，CUDA OOM 报错会直接导致整个 FastAPI 主进程被操作系统强制杀死崩溃，导致整个质检网关瘫痪。

而我们引入 Celery 分布式任务队列：

物理隔离：FastAPI 收到请求后只向 Redis 发送任务单，秒级返回，主进程永远不参与推理计算，绝对防爆。

物理限流：把 GPU 推理外包给独立的 Celery Worker 进程，并在启动时强行设置 --concurrency=1（单进程单并发）。无论前台堆积了多少质检任务，GPU 永远在后台有条不紊地‘串行排队、一个一个执行’。将显存开销死死锁在 $2\text{GB}$ 的红线之内，彻底从物理根源上消除了显存 OOM 崩溃的惨剧。”

### ⑤ Redis 干什么？

#### 一句话大白话：

“Redis 在我的系统里身兼三职：它是 Celery 传输任务的‘高速传送带（Broker）’，是存放算法结果的‘大临时仓库（Result Backend）’，还是阻挡高频流量、防止通达信封我 IP 的‘风控防爆缓存’。”

#### 专业级话术：

“在我们的分布式架构设计中，高性能内存数据库 Redis 承担了三个核心角色：

消息中间件（Message Broker）：作为 Celery 的传送带，在 FastAPI（生产者）与后台独立的 GPU 算法 Worker（消费者）之间，提供极高吞吐量的、异步非阻塞的任务排队通道。

结果后端（Result Backend）：高频保存 GPU 算法运行完后的结构化 JSON 结果，方便前端流式接口（SSE）随时读取和轮询。

高频行情缓存层：由于通达信等金融行情接口对每秒请求频次有严格限制。我们利用 Redis 的 Key-Value 缓存机制，对个股实时价格设置 1 秒的过期缓存（TTL）。1 秒内的重复查询直接在 Redis 内存中截断并返回，避免了高并发下频繁撞击外部行情柜台、导致 IP 被物理封禁的灾难。”

### ⑥ Docker 怎么部署？

#### 一句话大白话：

"我用 Docker 实现了‘环境集装箱隔离’，并且为了防止 PyTorch 镜像太大，自研了‘多阶段构建’，一刀砍掉 60% 的体积，再用 --gpus all 帮容器连上物理显卡跑模型。"

#### 专业级话术：

“我们通过将项目中的 FastAPI、Redis、Celery Worker 进行全栈容器化编排部署，彻底解决了‘环境地狱（Dependency Hell）’的隐患。

我的容器化部署有两个核心工程亮点：

多阶段构建（Multi-stage Build）：深度学习镜像通常高达 $15\text{GB}$，传输部署极其痛苦。我的 Dockerfile 将‘编译’与‘运行’彻底分家。在 builder 阶段使用包含完整 gcc 编译链的 CUDA-devel 镜像安装依赖并编译 Wheels；在 runtime 阶段只用干净、极轻量的生产运行时镜像，过河拆桥、把编译好的依赖物理 COPY 过来。将镜像最终体积强力压缩了 60% 以上。

GPU 穿透调用机制：在 docker-compose.yml 编排中，我们声明了 driver: nvidia、并保留了 gpu capabilities 资源预约。这会在宿主机与容器之间拉起 NVIDIA Container Toolkit 桥梁。强制在容器内挂载 /dev/nvidia 物理硬件设备文件，并以 bind-mount 方式将宿主机驱动层的 libcuda.so 透传注入到容器中，让容器内的 PyTorch 能以近乎 0 损耗的效率直接调用物理显卡的算力。”

### ⑦ Git 怎么协作？

#### 一句话大白话：

“我们团队用标准的 Git Flow 开发流程，有新功能就在独立的 feature 分支上写，合并前必须做 Code Review，冲突在本地解决好再提交。”

专业级话术：

“在团队研发协作中，我们严格遵循标准的 Git Flow 工作流 进行分支管理：

主干管理：master/main 分支作为生产环境的绝对洁净发布轨，develop 分支作为日常开发的合并轨。

特性开发：每当我需要开发新的算法模块（如草莓特征提取）或持仓诊断功能时，我会从 develop 检出独立的 feature/strawberry-feature 分支进行本地沙盒开发。

合并控制（PR/MR）：开发自测通过后，我会向 develop 提起 Merge Request。团队必须进行 Code Review，代码审计无误后才允许合入。

冲突解决原则：如果多人并发改动发生 Merge 冲突，我们严格禁止在远程分支上进行野蛮 merge。我会在本地将最新的 develop 拉回我的特性分支（git pull origin develop），在本地的 Cursor 中对冲突代码块进行逐行对齐、比对调试，确保编译运行 100% 通过后，再推送干净的 commit 提请合并，最大化维护了分支树的历史洁净度。”

### ⑧ Prompt 怎么设计？

#### 一句话大白话：

“我的 Prompt 采用结构化积木设计，给角色、给规则、给开卷考试的资料、给格式约束，求着大模型按我给的模具里‘填空’。”

专业级话术：

“在我的项目中，Prompt（提示词工程）设计遵循**‘结构化积木与强约束机制’**。一个高标准的工业级 Prompt 必须包含以下四个核心物理维度：

角色定义（Role & Tone）：明确告知模型它当前的专家身份，如‘你是一个拥有10年经验的金融风控审计专家’，收敛其概率采样的语言风格。

动态上下文注入（Context - 开卷资料）：将结构化 RAG 捞出的 Markdown 财务报表、K 线实时表格作为 [CONTEXT] 强制包裹，命令模型必须‘根据已知事实回答，禁止脱离事实自行发挥’。

输入引导（User Query）：传递经过前端正则清洗后的、干净的用户真实意图。

刚性边界约束（Constraints & Guardrails）：强力灌入 Few-Shot（少样本示范），并使用 XML 标签锁死输出格式。例如：‘你必须严格返回如下格式的 JSON 字符串，禁止输出任何正文、道歉或过渡性词汇’。

通过这种结构高度闭环的 Prompt 设计，将大模型原本天马行空的‘写作文模式’强行扭转为高度聚焦的‘填空题模式’，在前端渲染前就完成了第一道降噪。”


### ⑨ JSON Schema 为什么能降低幻觉？

#### 一句话大白话：

“大模型写作文时容易胡编乱造，但如果强迫它做‘选择题/填空题’，只在给定的框框里填词，它的幻觉空间就被压缩到了最极限。”

#### 专业级话术：

“这涉及到大模型概率采样的‘解密空间收缩（Search Space Reduction）’。

如果让大模型输出自由文本，它在生成每一个 Token（词）时，面临的是全网几百万个词汇的概率分布（词表空间过大，极易发生事实幻觉和格式发疯）。

而当我们引入 JSON Schema 约束（甚至开启原生的 Structured Outputs 结构化输出）时：

在 Prompt 层面：大模型被强行灌入了对数据类型的严格预期（必须有 action、confidence，且必须是 float/string）。

在 API 传输与解码层面：其底层（如 OpenAI 接口或 vLLM 采样层）会启用 Logits 掩码处理器（Logits Processor Mask）。

当大模型在输出完前缀 "action": " 之后，解码器状态机知道下一个字符只能在 "PASS"、"REJECT"、"STANDBY" 之间产生。Logits 掩码器会将词表中所有其他不相干词汇（如‘可能’、‘下跌’）的采样概率强行归零。

这种在字节码采样级别的刚性概率引导，在数学层面上将大模型生成下一个词的搜索空间缩减了 $99.9\%$ 以上，从根本上杜绝了胡言乱语的概率，确保了输出的绝对合法性与极低的幻觉率。”


### ⑩ 为什么选择 SSE 而不是 WebSocket？

#### 一句话大白话：

“在我的项目里，数据都是‘后端高频发、前端只管听’的纯单向传输。用轻量级的标准的 HTTP-SSE，既能流式显示进度，又不用去碰 WebSocket 那些复杂的断线重连、协议转换和防火墙封锁，省心又抗造。”

#### 专业级话术：

“这属于对技术协议开销与业务数据流特征的精准权衡。

WebSockets 采用的是双向全双工通信（Full-Duplex）：它要求客户端与服务端进行双向高频互动（如联机游戏、多人协作文档）。这需要长连接在初始化时，强行从 HTTP 协议升级（Upgrade）到 ws/wss 协议。在企业内网或微服务网关（如 Nginx、K8s Ingress）中，这往往需要配置昂贵的粘性会话，且极易被公司的局域网安全防火墙物理屏蔽。

而 SSE（Server-Sent Events，服务器发送事件）则是标准的、基于普通 HTTP 协议的单向事件流：

天然契合业务：不管是大模型逐字吐字，还是 3D 质检系统的‘预处理 $\rightarrow$ 推理 $\rightarrow$ 决策’阶段更新，数据流都是纯粹的**“后端单向广播 $\rightarrow$ 前端大屏渲染”**。前端完全没必要主动向后端发送高频字节，SSE 的单向性完美契合了业务。

轻量与自愈：由于 SSE 就是普通的 HTTP 连接（Content-Type: text/event-stream），它能 100% 穿透任何防火墙和反向代理。更硬核的是，SSE 是浏览器原生内置支持的，一旦网络抖动断线，浏览器会自发启动自动指数退避重连（Auto-reconnect），无需我们在前端用 JS 苦哈哈地去手写复杂的重连心跳检测。因此，它是我们高并发流式传输的最优工程解。”
