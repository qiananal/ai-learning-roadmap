## 结构化 RAG（时序/表格 RAG）与传统向量 RAG 的高阶鸿沟

### 1. 什么是 RAG？（从开卷考试说起）

大模型虽然聪明，但它的知识是有截止日期的，而且它记不住你私人的账本。

RAG（Retrieval-Augmented Generation，检索增强生成），通俗来说就是给大模型做“开卷考试”：

用户提问（如：“我的持仓比亚迪今天走势如何，需要减仓吗？”）。

系统去后台翻书（检索阶段，捞出比亚迪今天的价格、K线、你的成本）。

把翻到的书页贴在问题后面（增强阶段，组装成提示词）。

大模型看着书本回答问题（生成阶段，输出诊断报告）。

在“怎么去后台翻书”这一步，行业里分裂成了两条完全不同的技术路线：传统向量 RAG 与 结构化 RAG。

### 2. 传统向量 RAG 的底层原理与三大致命死穴

传统向量 RAG 的核心思想是“语义相似度匹配”。它处理非结构化文本（如 PDF、Word）非常拿手，但它的工作流程极其繁琐：

🛠️ 传统向量 RAG 工作流：

 原始 PDF ──► 文本切片 (Chunking) ──► 向量化 (Embedding) ──► 存入向量库 (Qdrant)

                                                                 │

 最终 LLM ◄── 拼接 Context ◄── 向量相似度检索 (Cosine Search) ◄────┘

#### ❌ 为什么向量 RAG 在 AxiomFin（金融盯盘中台）里会死得极惨？

##### 1. 致命死穴一：数学上的“数字钝化”（数字不敏感）

向量化（Embedding）的核心是将一句话压缩成一个高维数学向量（例如 1536 维的浮点数数组）。在这个高维空间里，向量检索计算的是“语义相近度”，而不是“数学精准度”。

例如：
向量模型会将 "持仓均价: 30.5 元" 和 "持仓均价: 30.6 元" 转化为几乎完全相同的两个高维向量。
在进行余弦相似度计算时：

$$S_C(\vec{A}, \vec{B}) = \frac{\vec{A} \cdot \vec{B}}{\|\vec{A}\| \|\vec{B}\|} \approx 0.9999$$


对于向量数据库来说，这两句话没有任何区别。但在金融交易中，0.1 元的差额乘以 10 万股，就是整整 1 万元的真实盈亏！ 向量 RAG 会直接导致大模型把你的买入成本和实时股价算错，诊断报告直接变成废纸。

##### 2. 致命死穴二：时间维度的“高频灾难”（时效性滞后）

股票市场的现价和成交量是毫秒级高频变动的。

如果采用向量 RAG：每次通达信的价格跳动，你都必须重新对个股行情进行文本拼接、调用 Embedding 接口（产生网络延迟和 Token 费用）、再重新写入 Qdrant 建立索引。

物理瓶颈：建立向量索引（Index Rebuild）是一个极度消耗 CPU 的计算过程。高频更新会导致服务器瞬间 CPU 100% 锁死，系统彻底瘫痪。


##### 3. 致命死穴三：表格结构的“切片粉碎”（结构丢失）

K线数据本质上是一个高维矩阵（包含开盘、收盘、高、低、成交量等）。

传统向量 RAG 在切片（Chunking）时，会暴力地按字符数把数据切断。这会直接把一张完整的 K 线历史表格切成两半，大模型拿到碎片后，根本无法拼回原貌，技术指标（MA, MACD）全部失效。

### 3. 结构化 RAG（Structured RAG）底层原理

既然向量 RAG 碰壁了， AxiomFin 项目里采用的 结构化 RAG 是怎么降维打击的？

它的核心思想是：“**放弃向量库，利用物理 API 直连 + 内存结构化组装**”。

🛠️ 结构化 RAG 工作流：

    1巡检线程启动 ──► 2. 物理直连通达信 API (pytdx) ──► 3. 捞取 120 日 K 线与盘中因子 (DataFrame)
   
                                                                       │

    6最终安全诊断 ◄── 5. LLM 推理 ◄── 4. 组装为 Markdown 干净表格 ◄──────┘

#### 为什么结构化 RAG 能在金融中台里完美闭环？

绝对精度（$\pm0.00$ 误差）：数据从通达信取出后，直接在 Python 内存中以 float 形式计算，拼装提示词时数字原封不动喂给大模型，避开了 Embedding 向量化带来的精度损失。

极速响应（毫秒级同步）：不需要调用第三方 Embedding API，不需要写向量库。数据在内存中直接拼接，整盘响应时间在 $100\text{ms}$ 以内，满足高频巡检需求。

结构高度完整（Markdown 渲染）：把时序数据转化为标准的 Markdown 表格文本：

| 日期 | 收盘价 | MA5 | MACD金叉 |

| 2026-03-01 | 30.50 | 30.12 | True |

大模型的 Attention（注意力）机制能够完美识别表格的行列关系，做到 100% 精准分析，彻底消除幻觉。

### 🎯4. 技术面试现场：面试官的“夺命连环炮”你怎么接？

#### 追问 1：现在人人都在简历里写向量数据库（Qdrant / Milvus）做 RAG，为什么你的金融中台里一个向量数据库都没用？是你不会用吗？

满分回答： “不是不会用，而是出于对金融业务场景与数据特征的深刻理解做出的主动架构取舍。

向量数据库（Vector DB）的核心价值在于非结构化长文本（如公司财报、政策文档）的语义关联检索。但金融盯盘与账户盘点场景面对的是高频变动、对精度要求达到小数点后两位、且具备强时序特征的结构化数值数据。

如果强行将这些数字向量化，首先，向量相似度计算在数学上存在‘数字钝化’，无法区分类似 $30.5$ 和 $30.6$ 元的微妙价差，会带来致命的计算幻觉；

其次，秒级高频变动的行情如果频繁写入向量库重构索引，会造成极高的 I/O 损耗和服务器 CPU 锁死。

因此，设计了结构化动态 RAG 架构，通过后台异步线程直连通达信 API 获取高频时序数据，并在内存中直接拼装为结构化的 Markdown 实体上下文注入模型，在保证 $100\%$ 数学精度的同时，实现了毫秒级的超低延迟同步。”

#### 追问 2：你的结构化 RAG 确实解决了数字精度问题，但如果用户问了一个宽泛的、非结构化的问题（比如：“沪电股份这家公司最近有什么行业利好和供应链风险吗？”），你这个系统不就失效了吗？

回答：“这正是我们系统未来的混合 RAG（Hybrid RAG）演进方向。

针对您提到的非结构化行业舆情与供应链风险，这属于非结构化数据的检索。我的架构预留了双路由通道：

对于‘价格、持仓、技术指标’等高频刚性数据，走结构化 RAG 通路，直连 API 计算；

对于‘研报、利好新闻、工商风险公告’，系统会启动向量 RAG 备用通路。利用 Embedding 将文本切片存入本地轻量级向量库，通过语义相似度捞取背景知识。

最终，中台会将‘结构化财务表格’与‘非结构化语义文本’在 Prompt 层面进行多源上下文融合（Multi-Source Context Fusion），再统一呈递给大模型。这样既保证了技术面指标的绝对精准，又提供了基本面大盘的宏观视野。
