# 核心痛点：为什么世界上需要 Docker？
在做 AI 项目（比如你的草莓质检系统或者 YOLO 项目）时，你一定经历过配环境的痛苦：

你的电脑是 Windows 11，安装了 Python 3.9，PyTorch 1.12，加上一堆显卡驱动。

如果现在要把这套代码拿到学校的 Linux 服务器上跑，或者导师让你部署到实验室的边缘设备上。

你必须在新的机器上把 Python、PyTorch、各种库重新装一遍。结果新机器因为操作系统不一样、或者某个库的版本冲突，疯狂报错。

这就是软件工程界最经典的噩梦：“在我的电脑上明明能跑啊，为什么换台机器就崩了？”

# Docker 的终极解法：集装箱（Container）

Docker 发明出来的灵感，来自于现实生活中的海运集装箱。

在没有集装箱之前，码头运货物非常痛苦：运钢琴的怕磕碰，运香蕉的怕腐烂，运化工品的怕泄漏。码头工人得针对每种货物精心设计不同的搬运和存放方式。

后来，人们发明了集装箱。不管你里面装的是香蕉、钢琴还是化学品，到了码头，只要把它们塞进标准的铁盒子里。码头上的吊车、货轮、卡车只认集装箱，不认里面的东西。

对应到代码里：

Docker 就是那个标准的集装箱。

它把你的 main.py（核心代码）、Python 3.10（解释器）、PyTorch（依赖库）甚至连操作系统最底层的工具，全部塞进一个虚拟的铁盒子里。

任何一台电脑（不管是大厂的云服务器、你自己的 Windows，还是边缘端设备），只要它安装了 Docker 软件（相当于码头上的吊车），它就能一键把这个铁盒子拉起来运行。里面的代码在运行的时候，根本不知道、也不在乎自己是在谁的电脑上跑，它只知道自己在一个安全的铁盒子里。

这就实现了：一次打包，到处运行。

# Docker 的运作流程：网吧的“无盘系统”

为了让你在面试时能说清楚 Docker 是怎么工作的，我们在脑子里建立第二张画面：网吧的系统。

去网吧上网时，你开机看到的 Windows 系统、里面的《英雄联盟》游戏，其实都不在你的这台电脑的主机里，而是在网吧服务器的“镜像”里。

Docker 的运行也是由三部分组成的：

### 1. Dockerfile（配方说明书）

它就是一个普通的文本文件（也就是我刚才让你建的那个）。它就像一张建筑图纸或者做菜配方。里面用大白话写着：“第一步，去拉取一个干净的 Ubuntu 系统；第二步，在里面安装 Python；第三步，把我的代码放进去。”

### 2. Image（镜像 - 游戏安装包 / 模板）

当你让 Docker 顺着 Dockerfile 这张图纸去建造，建出来的成品就叫 Image（镜像）。
它就像网吧服务器里的游戏镜像（或者一个只读的固态硬盘）。里面装满了操作系统、Python 环境、PyTorch 库和你的代码。这个镜像文件是死（静态）的、只读的，你不能直接进去改它。

### 3. Container（容器 - 正在运行的游戏实例）

只有安装包是不行的，游戏得跑起来。当你输入运行命令时，Docker 就会把这个 Image（镜像）加载到内存里，瞬间变成一个活的、正在运行的独立空间，这个空间就叫 Container（容器）。

你可以从一个 Image（安装包）里，同时拉起 10 个一模一样的 Container（容器）。它们互相独立，就像网吧里 10 台电脑同时在跑同一个游戏镜像，1号机里的玩家把游戏卸载了，绝对不会影响到2号机的玩家。


# 实操演示：

如果没有安装： 需要去 Docker 官网下载一个 Windows 版本的 Docker Desktop 并安装。

如果已经安装： 请双击打开它。必须确保这只小鲸鱼在你的电脑后台彻底变成绿色（显示 Engine Running）


### 第一步：在 VS Code 里创建这个“菜谱文件”

确保你在 ai-learning-roadmap 这个项目的目录下。

在空白处右键选择 新建文件，或者点击那个带加号的新建文件小图标。

把这个文件命名为 Dockerfile。(为了我的仓库的简洁性，我将其放在了Docker文件夹下。)

注意： 首字母 D 大写，后面全部小写。绝对不要加任何后缀名（不要写成 Dockerfile.txt 或 Dockerfile.py）。

成功建立后，它的图标在 VS Code 里通常会变成一个蓝色的小鲸鱼 🐳 或者一个标准的配置文件图标。

### 第二步：把“做菜步骤”写进文件里

双击打开你刚刚建好的 Dockerfile（现在里面是一片空白）。

请把下面这段工业界的标准 Python/AI 部署菜谱，复制黏贴到这个文件里：

    # 1. 基础环境：直接从云端拉取一个做过 AI 优化的官方 Python 3.10 环境
    FROM python:3.10-slim

    # 2. 设置工作目录：在集装箱内部自动建一个叫 /app 的文件夹，并走进去
    WORKDIR /app

    # 3. 复制依赖清单：把本地的依赖列表先单独复制到集装箱里
    COPY requirements.txt .

    # 4. 安装依赖：在集装箱内运行 pip 安装，换清华源加速，并清理缓存给集装箱瘦身
    RUN pip install --no-cache-dir -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple

    # 5. 代码拷贝：把本地当前文件夹下的所有核心代码，全部复制进集装箱
    # 就算Dockerfire文件不在根目录下，这里也不用动
    COPY . .

    # 6. 接口开放：告诉外部，这个集装箱运行起来后，会占用 8000 端口
    EXPOSE 8000

    # 7. 启动命令：当集装箱被拉起运行（Container）时，默认执行的主入口脚本
    CMD ["python", "main.py"]

### 第三步：为“菜谱”准备必要的食材

因为我们的菜谱里提到了 requirements.txt（依赖清单）和 main.py（核心入口），如果你的文件夹里没有这两个文件，Docker 待会儿打包时就会因为“找不到食材”而报错。

我们顺手在 Dockerfile 的同级目录下补齐它们：

#### 1.新建一个叫 requirements.txt 的文件，在里面写上你这个项目（或未来 AI 项目）最常用的三个库（一行一个）：

    fastapi
    uvicorn
    numpy

#### 2.新建一个叫 main.py 的文件，在里面写上一行最简单的 Python 代码作为入口：

    print("Hello MLOps! 你的第一个 Docker 镜像运行成功啦！")

#### 3.打包

    docker build -t my-ai-app -f docker/Dockerfile .

    docker build：Docker 给我编译一个集装箱镜像。
    -t my-ai-app：给这个镜像起个名字叫 my-ai-app。
    -f docker/Dockerfile：-f 代表 file（文件）。强行指定路标，告诉 Docker：“菜谱在 docker 文件夹里面，你去那里读。”
    .（最核心的盲点：最后这个小圆点！）：代表当前目录（根目录）。告诉 Docker：“以最外层根目录作为你的总基地，把这里的 main.py 和所有代码全部打包带走！”

这时候你会看到终端开始疯狂滚动蓝色或黑色的日志，它正在顺着你的 Dockerfile 菜谱一层一层地把 Python 环境、requirements.txt 里的依赖包（FastAPI、NumPy 等）下载并打包。

当它全部跑完，最后出现类似 FINISHED 或者 Naming to ... my-ai-app 的字样时，就说明镜像（Image）正式搓出来了！

### 既然打包成功了，怎么在电脑里看到这个活生生的镜像呢？有两种方法：

方法 A（极简可视化）： 直接打开你刚刚弄好的 Docker Desktop 软件界面，点击左侧的 Images 标签页。你会惊奇地发现，列表里多出了一个名字叫 my-ai-app 的新镜像，后面还写着它的大小（Size）。

方法 B（命令行）： 在 VS Code 终端里输入命令：
    docker images
它会啪地一下把电脑里所有的镜像罗列出来，第一行绝对就是你的 my-ai-app。

### 4. 运行容器（Container）

有了静态的镜像（安装包）还不够，我们必须让它在铁盒子里真正跑起来，变成一个活着的容器（Container）。

在 VS Code 终端里输入这行运行命令：

    docker run --name my-running-app my-ai-app

    这行命令的“大白话翻译”：

    docker run：Docker，给我把集装箱跑起来！

    --name my-running-app：给这个跑起来的活体容器起个名字，叫 my-running-app（不加这个参数的话，Docker 会随机给它分配一个搞笑的英文名字，比如“愤怒的爱因斯坦”）。

    my-ai-app：指定用哪一个镜像作为模板来运行。

### 删除
    docker rm my-running-app
