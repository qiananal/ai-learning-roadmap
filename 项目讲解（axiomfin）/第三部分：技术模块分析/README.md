## 第三部分：技术模块分析

根据当前真实代码，项目核心技术模块包括：

- LangChain Agent与Tool Calling
- Pydantic结构化参数校验
- DeepSeek模型调用与Prompt
- MCP Server
- PyTDX行情与NumPy指标计算
- Streamlit前端
- SQLite Agent审计
- JSON业务数据与线程锁
- 多线程与后台任务
- Mock降级、测试与评估

项目没有使用RAG、向量数据库、Celery、Redis、LangGraph；FastAPI虽然在依赖中，但没有实际接口实现。

### 1. LangChain Agent与Tool Calling

#### 为什么使用？

用户输入的是自然语言，而后端提供的是明确的业务函数。LangChain负责把这些工具描述转换成模型可理解的Tool Schema，并解析DeepSeek返回的Tool Call。

实际链路是：
```text
用户问题
→ DeepSeek判断意图
→ 生成Tool Call
→ LangChain解析工具名称和参数
→ 执行工具
→ ToolMessage返回模型
→ 模型生成最终答案
```

#### 项目里负责什么？

项目注册了11个LangChain Tools，包括：

- 股票代码查询；
- 实时行情；
- 企业风险；
- 邮件发送；
- 条件监控；
- 模拟交易；
- 每日选股；
- 精选缓存；
- 单股信号；
- 持仓诊断；
- 持仓告警。

Agent最多执行5轮，防止模型重复调用工具或陷入死循环。


#### 推荐回答

项目使用LangChain统一定义和绑定工具。模型产生Tool Call后，后端根据工具名称执行对应业务函数，再通过ToolMessage将结果放回上下文，模型基于真实数据生成答案。当前流程只有工具选择、执行和总结，所以没有引入LangGraph；如果以后出现复杂分支、人工审批和状态恢复，再考虑使用LangGraph。

#### 容易踩坑

不要说项目使用了LangChain的复杂AgentExecutor或LangGraph。当前实现是基于bind_tools的轻量Tool Calling循环。

### 2. Pydantic结构化参数校验

为什么使用？

大模型能够生成工具参数，但不保证参数一定合法。例如：

- 股票代码可能不是6位；
- 交易数量可能是负数；
- 操作类型可能不是BUY或SELL；
- 目标价格可能小于0。

Pydantic负责在工具执行前拦截这些错误。

#### 项目里负责什么？

项目定义了以下输入模型：
```text
股票查询参数；
股票代码；
企业名称；
邮件内容；
监控条件；
模拟交易；
单股信号分析；
Agent审计事件。
例如模拟交易要求：
action只能是BUY或SELL
stock_query不能为空
quantity必须大于0
股票代码会自动从sz002463中提取为002463，但不足6位会直接报错。
```

#### 推荐回答

Prompt只能降低错误概率，不能保证参数合法。项目使用Pydantic对模型生成的工具参数进行运行时校验，错误参数不会进入业务函数。Pydantic主要解决结构、类型和数值范围问题，不能保证模型的最终金融结论一定正确，所以行情和指标计算仍然由确定性代码完成。


### 3. DeepSeek模型调用与Prompt设计

#### 为什么使用？

模型负责理解用户表达和组织结果，例如把：“看看沪电现在能不能买”

映射成：analyze_stock_signals(stock_code="002463")

#### 项目里负责什么？
正式模式使用DeepSeek的OpenAI兼容接口，配置包括：

- API地址；
- 模型名称；
- API密钥；
- temperature；
- 超时和重试。

系统提示词会告诉模型：

- 它是金融投研Agent；
- 优先调用工具获取数据；
- 不允许自己编造行情和指标；
- 模拟交易不是真实券商下单；
- 每个工具的用途。

temperature设置为0.1，因为工具选择和参数生成更需要稳定性，而不是创造性。

#### 推荐回答

我把模型限制在意图理解、工具编排和结果解释三个环节。实时价格、技术指标和盈亏全部由Python工具计算，模型只能基于工具返回值回答。temperature设置为0.1，并配置超时和重试，减少工具选择的随机性。


#### 容易踩坑
不要把DeepSeek说成项目的股票预测模型。它没有预测股价，只负责Agent决策和语言生成。

### 4. MCP Server

#### 为什么使用？

Streamlit是项目自己的交互入口，但项目还希望让其他AI客户端使用行情和持仓分析能力，因此增加了MCP Server。

#### 项目里负责什么？

MCP对外提供5个工具：
- 实时行情查询；
- 技术分析；
- 带成本价的单股分析；
- 账户资产汇总；
- 持仓诊断。

MCP层不重新实现业务，而是复用现有的tools和services。
```text
外部AI客户端
→ MCP Tool
→ 现有业务服务
→ 返回JSON
```
内部LangChain Agent不经过MCP，而是直接调用本地工具。MCP是对外适配入口。

#### 推荐回答

MCP用于把现有业务能力标准化地提供给外部AI客户端。MCP层只做协议适配，实际分析逻辑仍然复用Service，避免维护两套实现。内部Agent为了减少调用链长度，直接使用本地LangChain Tools；MCP主要面向外部客户端。

#### 容易踩坑

capital_flow目前实际是账户资产、现金和持仓盈亏汇总，不是真正的市场主力资金流分析。

### 5. PyTDX行情与NumPy指标计算

#### 为什么使用？

项目需要实时行情和历史K线，才能完成选股、技术分析和持仓诊断。

PyTDX负责连接通达信行情服务器，NumPy负责数值计算。

#### 项目里负责什么？

行情数据包括：

- 当前价格；
- 昨收；
- 涨跌幅；
- 成交量和成交额；
- 开盘价、最高价、最低价；
- 历史日K线。
项目配置了多个行情节点，第一个连接失败后尝试其他节点。

NumPy计算的主要指标包括：

- MA5、MA10、MA20、MA60；
- RSI；
- MACD；
- 成交量均线；
- 支撑位和阻力位；
- 趋势斜率。

最终通过规则评分生成买入、观望或卖出信号。

#### 推荐回答
当前是可解释的规则型多因子系统，不是训练出来的机器学习模型。选股先用实时涨幅、成交量和成交额预筛，再对候选股票获取K线进行深度计算，减少行情请求。多个通达信节点用于故障切换。目前权重主要来自经验规则，尚未完成系统性回测，所以项目定位是投研辅助，不是实盘量化策略。

### 6. Streamlit前端
#### 为什么使用？

项目需要快速展示AI对话、资产看板、选股结果、持仓诊断和Agent调用轨迹，Streamlit可以直接使用Python完成这些页面。

#### 项目里负责什么？

页面包含：
- 左侧资产和告警面板；
- 每日精选Top5；
- 单股买卖信号；
- 持仓诊断；
- 智能投研助手；
- Agent调用链可视化。

聊天请求会放入工作线程，执行轨迹通过Queue传回页面。


#### 推荐回答
Streamlit适合快速构建Python AI应用原型，能够直接展示业务结果和Agent轨迹。当前页面会直接调用本地Service，不是严格的前后端分离架构。生产化时可以把Agent和业务能力拆成独立API服务，前端只负责交互。

#### 容易踩坑
不要说项目已经基于FastAPI实现后端接口。当前api目录是预留，FastAPI没有进入业务调用链。

### 7. SQLite Agent审计

#### 为什么使用？

Agent出现错误时，仅看最终回答很难知道问题发生在哪里，需要记录：
- 模型运行是否成功；
- 调用了什么工具；
- 参数是什么；
- 工具返回了什么；
- 是否发生异常。
- 项目里负责什么？
  
SQLite包含两张主要表：
```text
agent_runs
tool_calls
```
agent_runs保存用户问题、运行模式、状态、最终回答和错误。

tool_calls保存工具名称、参数、结果、成功状态和调用时间。

数据库启用了WAL模式，每次操作使用独立连接，并保证提交、回滚和关闭。

#### 推荐回答
SQLite主要用于Agent运行和工具调用审计，没有替代现有业务数据。这样可以较低成本实现调用复盘和错误定位。审计写入失败不会中断核心投研任务，Agent会记录错误并继续执行。

#### 容易踩坑
不要说SQLite是持仓交易数据库。当前持仓、监控和告警仍主要保存在JSON文件中。

### 8. JSON数据、线程锁与后台任务

#### 为什么使用？
项目是本地演示系统，数据量小，所以使用JSON保存持仓、股票池和监控任务。后台线程负责持续执行监控，不要求用户一直操作页面。


#### 项目里负责什么？

JSON文件保存：
- 用户持仓；
- 外部模拟盘同步数据；
- 股票池；
- 每日精选；
- 持仓告警；
- 监控任务。

线程锁用于保护同一进程中的关键文件读写。

后台任务包括：

- 每60秒检查监控条件；
- 每5分钟诊断持仓；
- 每30分钟刷新每日精选；
- Agent工作线程执行模型调用；
- Queue传递Agent轨迹。

#### 推荐回答
当前是单机演示项目，任务规模较小，所以使用守护线程和本地文件，避免引入Celery和Redis。项目通过进程内单例标志避免Streamlit重复启动线程，并用线程锁保护关键文件。但线程锁不能解决多进程竞争，生产环境需要独立任务调度、数据库和分布式锁。

### 9. Mock模式、测试与评估

#### 为什么使用？
面试现场可能没有稳定网络、行情节点或模型密钥，因此项目需要一个可重复演示的降级模式。

#### 项目里负责什么？

Mock模式提供：
- 5只固定股票的行情；
- 动态生成的历史K线；
- 本地Agent意图路由；
- 每日Top5；
- 真实技术指标计算。

Mock只替换外部数据和模型决策，业务计算仍然走正式代码。

测试覆盖：
- Pydantic参数校验；
- SQLite运行记录；
- LangChain Tool Calling循环；
- 真实FastMCP实例；
- Mock行情；
- 单股信号；
- Agent工具路由。
  

当前结果：
```text
9项单元测试通过
4/4 Agent路由评估通过
真实DeepSeek Tool Calling验证通过
```
#### 推荐回答
Mock替换的是外部行情和模型调用，但指标计算仍使用真实业务代码。Agent测试不能只比较最终文本，因为同一个正确答案可能有不同表达，所以项目分别测试工具路由、参数校验、工具执行和最终流程。目前评估集还比较小，后续应增加同义表达、错误参数、多轮对话和异常工具用例。


### 第三部分总结
这个项目最核心的技术主线不是某一个框架，而是：
```text
LangChain理解和调度工具
↓
Pydantic校验模型参数
↓
Python业务模块获取行情并计算指标
↓
ToolMessage将结构化数据交回DeepSeek
↓
Streamlit展示结果和调用轨迹
↓
SQLite记录Agent执行过程
↓
MCP向外部AI客户端开放能力
```

#### 面试中最重要的表述是：
项目将不确定的大模型决策与确定性的金融计算分开。模型负责理解意图、选择工具和解释结果；Pydantic负责约束参数；行情、指标和盈亏由Python业务模块计算；SQLite负责Agent审计，MCP负责对外提供标准化工具能力。
