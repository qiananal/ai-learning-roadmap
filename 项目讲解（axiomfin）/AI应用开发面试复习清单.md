# AxiomFin AI 应用开发面试复习清单

> 适用岗位：AI 应用开发、AI Agent 开发、LLM 应用工程师  
> 复习原则：先讲清项目为什么这样设计，再补充框架细节。回答时以本项目真实实现为准，不主动扩大项目能力。

## 使用方法

- `P0` 是必须熟练回答的内容，建议做到不看答案也能说清楚。
- `P1` 是面试官继续追问时常见的问题，需要理解实现细节。
- `P2` 是体现工程思考和改进能力的加分项。
- 每复习完一个问题，把标题前的 `[ ]` 改为 `[x]`。

# P0：必须掌握

## [ ] 1. 请用一分钟介绍这个项目

**参考回答：**

AxiomFin 是一个面向 A 股行情分析和个人持仓管理的智能投研系统。用户可以直接用自然语言询问股票价格、技术指标、买卖信号或者持仓风险。系统里的大模型不直接计算金融数值，而是负责理解用户意图、选择合适的工具，并根据工具返回的数据组织答案；行情查询、MA、MACD、RSI 和持仓盈亏等计算由普通 Python 模块完成。项目还通过 MCP 对外提供部分分析能力，通过 Streamlit 提供交互界面，并用 SQLite 记录 Agent 和工具的执行过程，便于排查问题。

## [ ] 2. 这个项目解决了什么问题？

**参考回答：**

它主要解决两个问题。第一，普通用户不需要记股票查询命令，可以直接用自然语言完成行情查询、技术分析和持仓诊断。第二，金融分析涉及大量准确数值，不能完全依赖大模型生成，因此系统把语言理解交给大模型，把行情获取和指标计算交给确定性程序，在使用方便和结果可靠之间做平衡。

## [ ] 3. 系统完整调用链是什么？

**参考回答：**

用户先在 Streamlit 页面输入问题，前端把对话历史交给 `AxiomFinEngine`。Engine 调用绑定了 Tools 的模型，模型根据问题返回普通文本或者工具调用请求。如果需要工具，系统先用 Pydantic 校验参数，再执行对应的行情或分析函数，把结果以 ToolMessage 返回给模型。模型结合工具数据生成最终回答。整个运行状态和工具调用结果同时写入 SQLite，执行轨迹通过 Queue 展示到页面。

```text
用户问题
  ↓
Streamlit 页面
  ↓
AxiomFinEngine
  ↓
LangChain 模型 + Tool Calling
  ↓
Pydantic 参数校验
  ↓
行情、指标、持仓等确定性工具
  ↓
ToolMessage 返回模型
  ↓
模型汇总结果
  ↓
页面答案 + SQLite 执行记录
```

## [ ] 4. 为什么不用大模型直接分析股票，而要调用工具？

**参考回答：**

大模型擅长理解用户表达和组织语言，但它不知道当前真实行情，也不适合精确计算金融指标。如果让它直接回答价格、MACD 或 RSI，很容易出现过期数据或者编造数值。工具可以读取行情并按固定公式计算，模型只负责决定调用什么能力以及如何解释结果，这样答案更稳定，也更容易追踪数据来源。

## [ ] 5. 大模型和普通业务代码分别负责什么？

**参考回答：**

大模型负责不确定的语言任务，包括理解意图、选择工具、生成参数以及汇总说明。普通业务代码负责确定性的任务，包括获取行情、计算技术指标、读写持仓、判断监控条件和记录审计。简单说就是“大模型做决策和表达，程序做查询和计算”。

## [ ] 6. LangChain 在项目中具体做了什么？

**参考回答：**

LangChain 在这里主要承担模型接入和 Tool Calling 的标准化。项目把本地函数包装成 LangChain Tools，再通过 `bind_tools` 把工具定义交给模型。模型返回工具名和参数后，Engine 执行工具并构造 ToolMessage，再交给模型生成最终回答。项目没有为了使用框架而引入复杂工作流，核心循环仍由自己的 Engine 控制。

## [ ] 7. Tool Calling 的完整过程是什么？

**参考回答：**

首先把工具名称、用途和参数结构提供给模型。模型理解用户问题后，如果需要外部数据，就返回要调用的工具和参数。程序校验参数并执行真实函数，再把执行结果作为工具消息放回对话。模型看到真实结果后生成用户能理解的答案。如果模型不需要工具，可以直接回答。

## [ ] 8. 项目有哪些 Tool，应该怎样分类？

**参考回答：**

项目中的 LangChain Tools 可以分为四类：行情类，如股票搜索和价格查询；分析类，如每日选股、买卖信号和持仓诊断；操作类，如模拟交易和添加监控任务；辅助类，如风险查询、邮件报告和告警查询。当前一共绑定了 11 个 LangChain Tools。分类的意义是让每个工具职责清楚，避免一个工具既查询又修改多种状态。

## [ ] 9. 如何让模型选对工具？

**参考回答：**

关键不是堆复杂 Prompt，而是把工具名称、描述和参数写清楚，让不同工具之间的职责尽量不重叠。例如“分析某只股票买卖点”对应信号分析工具，“看看我的持仓”对应持仓诊断工具。另外项目准备了典型问题做路由评估，检查模型或 Mock 路由是否选到了预期工具。

## [ ] 10. Pydantic 在项目里真正解决了什么？

**参考回答：**

Pydantic 主要约束模型生成的工具参数。例如股票代码必须是六位数字，交易方向只能是 BUY 或 SELL，数量必须大于零，涨跌幅和目标价格要在合理范围内。这样可以在进入业务函数之前拦截明显错误。需要注意，它约束的是工具入参，不代表模型最后生成的整段自然语言都经过了结构化校验。

## [ ] 11. 为什么金融指标必须放在确定性模块中计算？

**参考回答：**

因为同一组 K 线按照同一个公式计算，结果应该固定。让大模型计算不仅慢，而且可能算错、漏数据或者编造中间结果。项目使用 NumPy 对真实或 Mock K 线进行计算，再把结果交给模型解释。这样如果结果有问题，可以检查数据和公式，而不是面对一个无法复现的模型答案。

## [ ] 12. PyTDX 在项目中负责什么？

**参考回答：**

PyTDX 是行情数据入口，用来连接通达信行情服务器，获取实时行情和历史 K 线。业务模块拿到数据后再做指标和持仓分析。它只是数据源，不负责 Agent 决策。实际使用时还要考虑服务器连接失败、数据延迟、交易时段和复权方式等问题，所以项目提供了 Mock 数据作为演示降级方案。

## [ ] 13. 项目计算了哪些指标？为什么选择这些指标？

**参考回答：**

项目主要计算 MA、MACD、RSI 和支撑阻力位。这些指标能够覆盖趋势、动量、超买超卖和关键价格区间，比较适合展示一个完整的技术分析流程。项目的重点不是证明某个指标一定能赚钱，而是展示如何把行情数据转换成可解释的结构化分析结果。

## [ ] 14. NumPy 在项目中有什么价值？

**参考回答：**

NumPy 用来处理 K 线数值序列和技术指标计算。相比让模型处理数字，它速度更快、结果可复现，也便于测试。这个项目的数据量并不算特别大，所以使用 NumPy 已经够用，没有必要为了技术栈丰富再引入重型计算框架。

## [ ] 15. MCP 是什么？项目为什么使用 MCP？

**参考回答：**

MCP 可以理解成一套让 AI 客户端发现和调用外部工具的标准协议。项目使用 FastMCP 把行情查询、技术分析和持仓诊断等能力对外暴露。这样这些能力不只可以被 Streamlit 内的 Agent 使用，也能被支持 MCP 的其他客户端复用，减少客户端和业务实现之间的直接耦合。

## [ ] 16. MCP Tool 和 LangChain Tool 有什么区别？

**参考回答：**

它们底层可以复用同一批业务函数，但使用场景不同。LangChain Tool 是当前 Agent 进程内部供模型调用的工具；MCP Tool 是通过标准协议向外部 AI 客户端提供的能力。前者解决项目内部编排问题，后者解决跨客户端复用和标准化接入问题。不能把“使用了 MCP”说成“Agent 内部所有调用都经过 MCP”，本项目并不是这样实现的。

## [ ] 17. 项目的 MCP Server 提供了哪些能力？

**参考回答：**

当前 MCP Server 提供五个工具：股票价格查询、技术分析、带持仓成本的综合分析、账户资产信息查询和持仓诊断。它们复用了项目已有的业务函数，并不是重新实现一套分析逻辑。需要注意，代码中的 `capital_flow` 实际返回的是账户总资产、现金和持仓盈亏，不应在面试中说成市场主力资金流分析。

## [ ] 18. Streamlit 在项目中负责什么？

**参考回答：**

Streamlit 负责界面和交互，包括接收用户问题、展示分析结果、呈现 Agent 执行轨迹以及管理部分持仓和监控功能。选择它是因为开发速度快，适合 AI 项目原型和面试演示。它并不是独立的前后端架构，页面脚本重跑和长任务处理是需要额外解决的问题。

## [ ] 19. Streamlit 为什么会造成后台任务重复启动？

**参考回答：**

Streamlit 在用户交互时会重新执行页面脚本。如果把创建线程的代码直接写在普通页面流程里，每次重跑都可能再创建一个监控线程。项目通过任务状态控制，只允许相应后台任务启动一次，并使用守护线程执行循环任务，从而减少重复监控和重复告警。

## [ ] 20. 为什么使用 Queue 传递 Agent 执行轨迹？

**参考回答：**

Agent 和行情工具可能执行较久，如果直接在主页面流程里同步等待，界面体验会比较差。项目把任务放到后台线程执行，再用线程安全的 Queue 把“模型规划、工具调用、工具结果”等事件传回页面。这样执行逻辑和界面展示不需要直接操作彼此的状态，也降低了并发访问问题。

## [ ] 21. 线程锁解决了什么问题？

**参考回答：**

多个线程可能同时读写监控任务、持仓或告警数据。如果不加锁，一个线程读取时另一个线程正好写入，可能出现数据覆盖、文件内容不完整或者重复处理。锁让关键读写操作在同一时间只由一个线程执行。它适合当前单进程原型，但如果以后部署多个进程或多台机器，本地线程锁就不够了。

## [ ] 22. SQLite 在项目中保存什么？

**参考回答：**

SQLite 主要用于 Agent 执行审计，保存一次运行的用户问题、运行模式、状态、最终答案、错误信息，以及每次工具调用的工具名、参数、结果和是否成功。这样出现错误时可以复盘模型调用了什么工具、传了什么参数。它不是当前项目全部持仓业务数据的统一数据库，这个边界需要说清楚。

## [ ] 23. 为什么工具调用需要审计？

**参考回答：**

Agent 的行为不是完全固定的，同一句话可能因为模型判断不同而走不同工具。如果只保留最后答案，出错时很难知道问题在模型路由、参数、工具还是数据源。记录调用链后，可以定位错误、统计工具使用情况，也为后续做评估和优化提供数据。

## [ ] 24. 系统如何减少大模型幻觉？

**参考回答：**

项目主要做了四件事：真实行情和指标由工具提供；模型生成的工具参数用 Pydantic 校验；工具结果以结构化数据返回；执行过程写入审计记录。它们可以降低数值编造和错误调用，但不能完全消除幻觉，因此最终结果仍要带数据时间和风险提示，不能把系统描述成自动给出可靠投资建议。

## [ ] 25. 如果模型连续调用工具，如何防止无限循环？

**参考回答：**

Agent 循环必须设置最大轮数。每轮检查模型是否还返回工具调用，如果没有就结束并返回答案；如果达到上限仍未完成，则停止执行并返回可识别的异常或降级结果。同时应记录每轮工具调用，方便判断是 Prompt、工具描述还是工具结果让模型反复尝试。

## [ ] 26. 工具执行失败时系统应该怎么处理？

**参考回答：**

不能让整个页面因为一个工具异常直接崩溃。系统应捕获连接失败、参数错误和业务异常，把成功状态与错误原因写入审计，并给模型或用户一个明确的失败信息。行情不可用时可以使用 Mock 模式完成演示，但必须明确说明是模拟数据，不能把模拟结果冒充实时行情。

## [ ] 27. Mock 模式为什么是工程能力，而不只是造假数据？

**参考回答：**

行情服务器和模型 API 都依赖网络，面试现场不一定稳定。Mock 模式让工具调用链、参数校验、指标计算和页面展示仍然可以完整运行，从而把“系统逻辑是否正确”和“外部服务是否在线”分开验证。它同时有利于自动化测试，因为测试数据固定、结果更容易复现。

## [ ] 28. 项目如何测试 Agent，而不只是测试普通函数？

**参考回答：**

除了测试参数模型、存储和 MCP 工具是否可调用，项目还准备了典型自然语言问题，检查它们是否被路由到预期工具。例如“分析 002463 的买卖点”应该调用信号分析，“我的持仓怎么样”应该调用持仓诊断。现阶段主要验证工具选择，后续还可以增加参数正确率、答案引用准确率和异常场景评估。

# P1：重点掌握

## [ ] 29. 为什么项目自己写 Tool Calling 循环，而没有直接使用现成 AgentExecutor？

**参考回答：**

自己的循环更容易控制最大调用轮数、日志格式、SQLite 审计和前端执行轨迹，也更容易看清模型消息与工具消息是怎样往返的。这个项目流程相对简单，不需要引入更重的抽象。代价是异常恢复、并行工具和复杂状态管理需要自己处理。

## [ ] 30. ToolMessage 有什么作用？

**参考回答：**

ToolMessage 是把工具执行结果放回模型上下文的标准消息。它会带上对应的调用标识，让模型知道这个结果属于哪一次工具请求。没有这一步，模型虽然提出了调用要求，却看不到真实结果，也就无法基于行情数据完成最后总结。

## [ ] 31. 为什么 Tool 的描述非常重要？

**参考回答：**

模型主要依靠工具名、描述和参数说明来判断何时调用。描述太模糊，模型容易选错；多个工具描述高度重叠，模型也容易摇摆。好的描述应说明工具能做什么、不能做什么、需要什么参数以及返回什么信息，但不用写成很长的业务文档。

## [ ] 32. 如何设计一个好的 Tool？

**参考回答：**

一个工具最好只承担一个清楚的业务职责，参数数量适中，名称与用户意图容易对应，返回值结构稳定，并且错误可以被识别。涉及写操作的工具还应增加确认、幂等和权限控制。本项目中的模拟交易和添加监控任务属于有副作用的工具，比单纯行情查询需要更谨慎。

## [ ] 33. 查询型 Tool 和操作型 Tool 的风险有什么不同？

**参考回答：**

查询型工具通常只读，调用错误主要导致答案不准确；操作型工具会修改持仓、增加任务或发送邮件，误调用可能产生实际影响。因此操作型工具应该做更严格的参数校验、用户确认、幂等控制和权限检查。项目目前更适合作为模拟投研系统，不能直接宣传成真实自动交易系统。

## [ ] 34. 项目中的 Prompt 应该重点约束什么？

**参考回答：**

Prompt 应明确模型的角色、可用工具、必须优先使用工具获取金融数据、不能编造行情、如何引用工具结果以及投资风险边界。对于已经能由工具描述和参数模型表达的内容，不必全部重复写进 Prompt。Prompt 的目标是规范决策，不是代替业务代码。

## [ ] 35. 多轮对话历史有什么作用？

**参考回答：**

对话历史让模型理解省略信息。例如用户先问某只股票，下一句只说“那它的 RSI 呢”，模型需要从历史中知道“它”指哪只股票。但历史不能无限增长，否则成本和干扰都会增加。生产系统通常会做消息截断、摘要或按任务保留相关上下文。

## [ ] 36. 工具返回 JSON 有什么好处？

**参考回答：**

结构化结果比一大段自然语言更容易被模型正确引用，也方便前端展示、审计和测试。例如价格、涨跌幅、RSI 分成明确字段，比把所有信息拼在一句话里更可靠。结构稳定后，未来更换模型或客户端也更容易。

## [ ] 37. 为什么 SQLite 使用 WAL？

**参考回答：**

WAL 模式可以改善读写并发，读操作通常不需要一直等待写操作完成，比较适合当前这种前端查询记录、后台又持续写审计的轻量场景。但 SQLite 仍然是单机数据库，写并发很高或多实例部署时应该考虑 PostgreSQL 等服务型数据库。

## [ ] 38. SQLite 事务在这里有什么意义？

**参考回答：**

一次数据库操作要么完整提交，要么失败回滚，避免只写入一半数据。项目通过连接上下文统一提交、回滚和关闭连接。审计记录本身不是核心交易账本，但保持记录完整仍然有助于正确排错。

## [ ] 39. 线程、进程和异步应该怎样选择？

**参考回答：**

本项目的模型请求和行情请求大多是网络等待，线程实现简单，也便于和 Streamlit 配合，因此使用后台线程是合理的。若任务是大量 CPU 计算，多进程更合适；若系统改成高并发 API 服务，异步 I/O 通常更有优势。选择依据应该是任务特点，不是哪个技术听起来更高级。

## [ ] 40. 为什么守护线程适合当前项目？有什么问题？

**参考回答：**

守护线程不会阻止应用退出，适合原型中的监控和定时循环。但进程关闭时它可能被直接终止，不保证任务一定完成，也缺少持久化调度和失败重试。因此生产环境更适合把后台任务拆到独立任务系统或服务中。

## [ ] 41. MCP 如何做到复用已有业务逻辑？

**参考回答：**

MCP Server 的函数只负责协议层封装，真正的行情和分析仍调用 `tools` 与 `services` 中的业务函数。这样修复指标逻辑时只需要修改一处，Streamlit Agent 和 MCP 客户端都能复用，避免两套实现产生不同结果。

## [ ] 42. 为什么本地目录不能也命名为 `mcp`？

**参考回答：**

如果项目自己的包叫 `mcp`，Python 导入时可能优先找到本地目录，而不是官方 MCP SDK，最终出现模块被遮蔽的问题。项目把服务目录命名为 `mcp_server`，让 `from mcp.server.fastmcp import FastMCP` 明确导入官方包。这是一个实际遇到时很典型的 Python 模块命名冲突问题。

## [ ] 43. Streamlit 是否等于项目后端？

**参考回答：**

当前项目中 Streamlit 同时承担界面和一部分应用编排，但它不是标准意义上的独立后端服务。项目没有把核心能力包装成完整 FastAPI REST 服务。MCP Server 是另一种对外入口，但也不能把它说成传统业务 API 网关。

## [ ] 44. 如何判断技术指标计算是否正确？

**参考回答：**

首先用固定 K 线作为测试输入，验证计算结果可复现；其次和成熟行情软件或可靠库的同口径结果对比；还要确认周期、复权、缺失值和边界数据处理一致。只看最终买卖建议是否“感觉合理”是不够的，因为错误可能被自然语言包装掩盖。

## [ ] 45. 项目的实时行情真的完全实时吗？

**参考回答：**

不能绝对这样宣传。PyTDX 获取的是行情服务器提供的数据，实际新鲜度受服务器、网络、交易时段和接口能力影响。更准确的说法是“接入实时行情查询能力”，并在结果中标注数据时间。Mock 模式下更要明确说明数据是模拟的。

## [ ] 46. 如何保护模型 API Key？

**参考回答：**

密钥放在环境变量或本地 `.env` 中，通过 `.gitignore` 防止提交，仓库只保留示例配置。日志和异常中也不能打印完整密钥。如果密钥曾经出现在聊天、提交记录或截图里，应立即撤销并重新生成，而不是只从文件中删除。

## [ ] 47. 这个项目为什么没有使用 RAG 或向量数据库？

**参考回答：**

当前核心问题是查询行情和计算指标，数据来自结构化接口和本地持仓，并不是从大量非结构化文档中检索知识，因此 RAG 不是必要组件。如果以后加入研报、公告和财报问答，再考虑文档切分、向量检索和引用溯源更合理。

## [ ] 48. 这个项目为什么没有使用 LangGraph？

**参考回答：**

当前工作流主要是“模型决定工具—执行工具—返回模型”的循环，状态和分支不复杂，自定义循环足够清楚。若以后加入多 Agent、人工审批、任务暂停恢复、复杂分支和持久化状态，LangGraph 才会更有价值。没有必要为了简历关键词提前增加复杂度。

# P2：扩展与优化加分项

## [ ] 49. 如果把项目升级到生产环境，你会先改什么？

**参考回答：**

我会优先做四件事：把后台监控拆成独立任务服务；把本地文件和 SQLite 迁移到可靠数据库；给有副作用的工具增加鉴权、确认和幂等；完善行情缓存、超时、重试、指标测试和 Agent 评估。模型能力可以继续优化，但生产可靠性应该先补齐。

## [ ] 50. 如何支持更多用户同时使用？

**参考回答：**

当前单进程 Streamlit、线程和本地文件更适合演示。多用户场景需要把用户身份和数据隔离，把核心业务拆成 API 服务，把状态放到服务型数据库，把定时监控交给任务队列，并对行情结果做缓存。还要控制模型并发、费用和超时。

## [ ] 51. 如何优化响应速度和模型成本？

**参考回答：**

可以缓存短时间内重复的行情和分析结果，缩短无关对话历史，减少工具返回中的冗余字段，并让简单查询直接走工具而不是反复调用模型。对复杂分析再使用更强模型。优化前应该先记录耗时和 token 使用，找出真正的瓶颈。

## [ ] 52. 如何改进 Agent 评估？

**参考回答：**

现有评估主要检查工具路由。下一步可以建立固定问题集，分别统计工具选择准确率、参数正确率、工具结果引用正确率、最终答案完整性、延迟和成本。金融场景还要增加数据时间、数值一致性以及异常行情下的测试。

## [ ] 53. 如何提高系统可观测性？

**参考回答：**

在现有 SQLite 审计基础上，可以为每次请求分配统一 run_id，记录模型耗时、工具耗时、token、重试次数、错误类型和数据源。再做一个简单统计页面，就能看出哪个工具最慢、哪类问题最容易失败，而不是只靠用户反馈排查。

## [ ] 54. 如何处理行情接口不稳定？

**参考回答：**

需要设置连接和读取超时，对可恢复错误做有限次数重试，并准备多个行情节点或缓存数据。错误要明确区分“股票不存在”“非交易时段”和“数据源不可用”。Mock 只用于测试和演示，生产降级时应该标明数据时间，不能静默返回模拟行情。

## [ ] 55. 如何防止重复执行模拟交易或重复创建监控任务？

**参考回答：**

参数校验只能保证格式正确，不能防止同一请求重复执行。更稳妥的做法是为操作生成幂等键，执行前检查是否处理过；创建监控任务时按用户、股票和条件去重；涉及交易时必须二次确认，并记录操作审计。

## [ ] 56. 如果需要加入研报问答，架构怎样扩展？

**参考回答：**

可以新增一个独立的研报检索工具，内部负责文档解析、切分、向量检索和来源引用。Agent 仍然只负责判断用户是在问实时行情、技术分析还是研报内容。这样 RAG 是新增的一种工具能力，不需要推翻现有 Tool Calling 架构。

## [ ] 57. 项目最大的技术亮点是什么？

**参考回答：**

我认为最大的亮点不是用了多少框架，而是职责划分比较清楚：模型负责理解和编排，确定性模块负责金融数据和计算；同一批业务能力既能作为 LangChain Tools 使用，也能通过 MCP 对外复用；同时对参数、执行轨迹和异常做了校验与审计，形成了相对完整的 Agent 工程闭环。

## [ ] 58. 项目最大的不足是什么？

**参考回答：**

它目前仍然是单机演示型应用。Streamlit、后台线程、本地数据和 SQLite 在低并发下够用，但不适合多实例和高可靠部署。Agent 评估也主要覆盖工具路由，还缺少更完整的参数、数值引用和回答质量评估。另外技术指标只能提供辅助判断，尚未经过严谨回测，不能证明投资收益。

## [ ] 59. 如果面试官质疑“这只是套壳调用大模型”，怎么回答？

**参考回答：**

如果只是把问题发给模型再展示文本，确实是简单套壳。这个项目的工作重点在模型之外：设计工具边界和参数结构，接入行情并完成确定性指标计算，处理 Streamlit 后台任务和并发读写，通过 MCP 复用能力，再记录和评估 Agent 的实际调用过程。模型只是其中的意图理解与编排组件。

## [ ] 60. 如果让你重新做一次，你会怎样调整设计？

**参考回答：**

我会保留“模型编排、程序计算”的核心设计，但更早统一业务数据模型和错误格式，把工具结果从 JSON 字符串进一步规范成稳定结构；把只读工具和有副作用工具分级；补充基准数据测试和 Agent 离线评估。如果目标变成生产部署，再拆分 API、任务服务和持久化层。

# 简历描述边界：面试时不要说错

## [ ] 61. 能不能说项目使用了 Pydantic 约束模型输出？

**参考回答：**

更准确的说法是“使用 Pydantic 约束模型生成的工具调用参数”。当前最终回答仍然是自然语言，没有全部通过 Pydantic 输出模型校验。这样表达既符合代码，也能体现自己理解结构化输出和工具参数校验的区别。

## [ ] 62. 能不能说 SQLite 管理了全部持仓数据？

**参考回答：**

不能。SQLite 当前主要保存 Agent 运行和工具调用审计。面试时可以说它解决了调用链追踪和问题复盘，但不要把它扩大成完整的账户、交易和持仓数据库。

## [ ] 63. 能不能说项目实现了自动交易？

**参考回答：**

不能。项目有本地模拟持仓操作和买卖信号分析，但没有对接真实券商交易，也没有生产级风控和订单系统。更准确的表达是“模拟交易与持仓管理”。

## [ ] 64. 能不能说项目有资金流分析？

**参考回答：**

不建议。当前 MCP 中名为 `capital_flow` 的工具实际查询账户资产、现金和持仓盈亏，不是市场主力资金流。简历中应说“账户资产查询”或“持仓资产汇总”。

## [ ] 65. 能不能说项目使用了 FastAPI、Celery、Redis、RAG 或向量数据库？

**参考回答：**

不能，因为当前项目没有真实使用这些技术。可以在系统优化问题中说明未来为什么可能引入，但不要写进已实现技术栈。面试官一旦追问部署方式、任务确认、消息可靠性或检索评估，很容易暴露描述与代码不一致。

## [ ] 66. 哪些技术不要主动展开太深？

**参考回答：**

不要主动把技术指标包装成量化策略，不要声称经过回测并能产生稳定收益；不要把 MCP 说成复杂分布式微服务；不要把线程锁说成分布式锁；不要把 Mock 模式说成高可用灾备。可以如实说明它们解决了当前单机演示中的具体问题，并指出生产化需要怎样升级。
