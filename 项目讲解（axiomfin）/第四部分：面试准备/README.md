## 第七部分：面试准备

### 1. 请介绍一下这个项目

考察点： 能否快速讲清业务、技术架构和个人贡献。

推荐回答：

AxiomFin是一个面向A股投研和个人持仓管理的AI Agent系统。用户可以通过自然语言查询行情、分析买卖信号、诊断持仓和创建监控任务。正式模式使用LangChain将11个业务工具绑定给DeepSeek，Pydantic负责参数校验，行情和技术指标由Python业务模块计算，SQLite记录Agent运行和工具调用轨迹，另外通过MCP向外部AI客户端开放部分能力。

容易踩坑： 一开始就罗列技术名词，没有说明解决什么问题。

更像真实做过： 主动说明“模型负责理解和编排，业务模块负责金融计算”。


### 2. 这个项目为什么属于Agent，而不是普通聊天机器人？

考察点： 是否真正理解Agent。

推荐回答：
普通聊天机器人主要根据上下文直接生成文本，而这个系统能够根据用户目标选择工具、生成参数、执行外部操作，再根据工具结果继续推理。例如用户问持仓情况时，模型会调用持仓诊断工具，而不是直接凭上下文回答。

容易踩坑： 把“调用一次LLM”也说成Agent。

更像真实做过： 说明项目包含“模型决策—工具执行—ToolMessage回传—模型总结”的闭环。

### 3. 为什么使用LangChain？

考察点： 是否为了框架而使用框架。

推荐回答：
项目最初可以通过手写JSON协议实现工具路由，后续使用LangChain统一工具Schema、Tool Call解析和ToolMessage构造，减少不同模型调用协议的适配代码。业务逻辑仍然独立于LangChain，避免框架侵入核心计算。

容易踩坑： 只回答“LangChain方便”。

更像真实做过： 强调LangChain只负责模型与工具之间的协议适配，金融计算仍在Service层。


### 4. Tool Calling的完整过程是什么？
考察点： 是否理解工具调用底层链路。

推荐回答：
```text
定义Pydantic参数模型
→ 将函数注册为LangChain Tool
→ bind_tools绑定给DeepSeek
→ 模型生成tool_calls
→ 后端根据名称找到工具
→ Pydantic校验参数
→ 执行业务函数
→ 构造ToolMessage
→ 再次调用模型生成答案
```

项目最多执行5轮，避免无限循环。

容易踩坑： 说模型自己执行了Python函数。模型只生成调用请求，真正执行发生在后端。

更像真实做过： 能说出Tool Call ID需要与ToolMessage对应。


### 5. Pydantic在项目中解决了什么问题？

考察点： 是否理解结构化输出和运行时校验。

推荐回答：
Pydantic用于校验模型生成的工具参数，例如股票代码必须是6位数字，交易操作只能是BUY或SELL，交易数量必须大于0，监控价格必须合理。它将模型输出从“不可信输入”转换成业务函数可接受的数据。

容易踩坑： 声称Pydantic可以消除模型幻觉。

更像真实做过： 说明Pydantic保证的是结构、类型和范围，不保证最终金融判断正确。

### 6. 如何降低大模型在金融场景中的幻觉？

考察点： 高风险业务中的可靠性设计。

推荐回答：
我没有让模型直接生成价格和计算技术指标。实时行情、均线、MACD、RSI和盈亏都由确定性Python代码计算，模型只能基于工具返回的结构化数据解释结果。此外使用低temperature、工具参数校验和工具调用审计降低错误风险。

容易踩坑： 回答“优化Prompt就可以避免幻觉”。

更像真实做过： 将风险拆成数据幻觉、参数错误和解释错误，分别用工具、Pydantic和审计处理。


### 7. 为什么没有使用LangGraph？

考察点： 技术选型能力。

推荐回答：
当前工作流主要是模型选择工具、工具执行、结果回传和最终总结，分支较少，普通Tool Calling循环已经够用。引入LangGraph会增加状态定义和维护成本。如果后续增加人工审批、多Agent协作、任务恢复或复杂条件分支，再迁移到LangGraph更合理。

容易踩坑： 说LangGraph没用或者自己写的一定更好。

更像真实做过： 从业务复杂度和状态管理需求解释选择。

### 8. 模型选错工具怎么办？

考察点： Agent可靠性与评估。

推荐回答：
首先通过清晰的工具名称、描述和参数Schema提高选择准确率。后端只允许调用注册表中的工具，非法工具不会执行。项目还对典型问题建立路由评估。如果工具选择错误，可以根据SQLite中的问题、工具名称和参数记录进行复盘。

容易踩坑： 认为模型选错后只能重新提问。

更像真实做过： 提到工具描述优化、评估集、错误反馈和审计闭环。

### 9. 如何处理非法工具参数？

考察点： 异常处理。

推荐回答：
LangChain Tool调用前由Pydantic验证参数。校验或业务执行失败时，后端捕获异常，将错误转换成工具结果返回给模型，同时写入SQLite。模型可以根据错误调整参数，或者明确告诉用户缺少必要信息。

容易踩坑： 使用大量try/except: pass隐藏错误。

更像真实做过： 区分参数校验失败、工具不存在、行情失败和业务规则失败。

### 10. 哪些工具属于高风险工具？

考察点： Agent安全意识。

推荐回答：
行情查询和技术分析属于只读工具；模拟交易、监控任务写入和邮件发送属于有副作用工具。当前模拟交易只修改本地账户，不连接真实券商。生产环境下，有副作用工具需要增加用户确认、权限控制、幂等键和审计日志。

容易踩坑： 说工具注册后可以完全交给模型自由调用。

更像真实做过： 主动提出只读工具与写操作工具分级。

### 11. MCP在项目中负责什么？

考察点： 是否真正理解MCP，而不是只会解释概念。

推荐回答：
MCP把项目已有的行情查询、技术分析、账户资产和持仓诊断能力提供给外部AI客户端。MCP层只做协议适配，实际业务仍复用Service。内部LangChain Agent直接调用本地Tools，不经过MCP。

容易踩坑： 说整个项目基于MCP运行。

更像真实做过： 明确区分内部工具调用链和外部MCP入口。

### 12. MCP和REST API有什么区别？

考察点： 协议理解。

推荐回答：
REST主要面向普通应用，通过固定HTTP接口提供服务；MCP面向AI客户端，除执行工具外，还强调工具发现、名称、描述和参数Schema，使模型更容易理解和调用能力。两者并不冲突，生产系统可以同时提供REST和MCP入口。

容易踩坑： 说MCP会替代所有REST API。

更像真实做过： 强调MCP是AI能力适配层，不应该承载重复业务逻辑。


### 13. 每日选股是机器学习模型吗？

考察点： 是否夸大算法能力。

推荐回答：
不是。当前是可解释的规则型多因子评分系统，包含量价关系、趋势、量能结构、突破形态和成交活跃度。每个条件对应固定分数，最后排序取Top5。这样结果容易解释，但目前还没有完整回测和参数寻优。

容易踩坑： 把固定规则说成训练模型或量化预测模型。

更像真实做过： 主动说明当前优势是可解释，局限是权重依赖经验。


### 14. 为什么不让LLM直接完成技术分析？

考察点： LLM与传统代码的职责边界。

推荐回答：
技术指标计算要求结果稳定且可重复，适合使用NumPy和明确公式。LLM不适合精确计算大量时间序列数据，所以项目让Python计算指标，让LLM负责理解需求和解释结果。

容易踩坑： 把所有业务逻辑都塞进Prompt。

更像真实做过： 说明确定性任务用代码，不确定性语言任务用模型。

## 15. 为什么设计Mock模式？
考察点： 降级能力和测试意识。

推荐回答：
行情服务器和模型API都属于外部依赖，面试现场可能出现网络或密钥问题。Mock模式提供确定性行情和动态生成的K线，但仍复用真实指标计算流程，因此既能稳定演示，也能测试核心业务链路。

容易踩坑： 说Mock只是返回一段固定答案。

更像真实做过： 强调Mock替换数据源和模型决策，不替换业务计算。

### 16. 为什么使用Streamlit？有什么不足？

考察点： 前端选型和生产化认知。

推荐回答：
Streamlit可以直接使用Python快速构建资产看板、分析页面和Agent轨迹，适合原型和面试展示。它的不足是当前前后端没有完全分离，多用户隔离和横向扩展能力有限。生产化时应该把Agent和业务服务拆成独立API。

容易踩坑： 说Streamlit天然适合高并发生产系统。

更像真实做过： 说明它是根据项目阶段选择的，而不是最终架构。

### 17. 如何避免Streamlit刷新后重复创建后台线程？

考察点： Streamlit运行机制和并发设计。

推荐回答：
Streamlit交互会重新执行页面脚本，所以项目在Streamlit模块对象上设置初始化标志。只有标志为False时才启动守护线程，从而避免每次页面刷新都创建新的监控线程。

容易踩坑： 把session_state当成跨进程全局单例。

更像真实做过： 说明当前方案只保证单进程内有效，多实例部署仍需要独立调度器和分布式锁。

### 18. 为什么同时使用JSON和SQLite？

考察点： 数据架构与权衡。

推荐回答：
JSON保存持仓、股票池、监控任务和告警，主要是为了本地演示和零数据库依赖；SQLite用于Agent运行和工具调用审计，方便复盘模型行为。这样改造成本较低，但不是最终生产方案。

容易踩坑： 说SQLite保存了持仓交易，当前代码并不是这样。

更像真实做过： 说明这是演示复杂度与工程可观测性之间的折中。

### 19. 项目如何测试Agent？

考察点： 是否有LLM应用评估意识。

推荐回答：
Agent不能只比较最终文本，因为同一答案可能有多种正确表达。项目分别测试Pydantic参数校验、SQLite记录、LangChain Tool Calling循环、FastMCP实例、Mock行情和工具路由。当前9项测试以及4个典型路由用例通过，还完成了真实DeepSeek Tool Calling验证。

容易踩坑： 只说“手动在页面问了几个问题”。

更像真实做过： 提到路由准确率、参数正确率、工具成功率和任务完成率应该分开评估。

### 20. 如果把项目部署到生产环境，你会怎么优化？

考察点： 系统设计和工程成熟度。

推荐回答：
我会优先做五项改造：第一，将Streamlit与后端服务分离；第二，将持仓、交易和监控任务迁移到关系型数据库；第三，用独立任务调度器替代页面进程内线程；第四，对有副作用工具增加权限、确认和幂等控制；第五，补充模型调用耗时、Token消耗、工具成功率和Agent任务完成率监控。之后再根据流程复杂度考虑LangGraph。

容易踩坑： 一上来就说微服务、Kubernetes、多Agent，缺少优先级。

更像真实做过： 先解决当前系统真正存在的数据一致性、任务可靠性和权限问题。
