## 第四部分：RAG 模块解释。

### 1. 为什么需要 RAG？

先说业务原因。

客服系统经常要回答这类问题：
这个商品支持 7 天无理由退货吗？
保修政策是什么？
发票怎么开？
这份售后说明里退款多久到账？

这些问题不能完全靠大模型自己的训练知识回答。

原因有三个：

第一，大模型不知道你上传的私有文档。
比如你公司内部的售后政策、商品说明、退货规则，大模型训练时不一定见过。

第二，业务规则会变。
今天支持 7 天退货，明天可能改成部分商品不支持。只靠模型训练知识很容易过时。

第三，客服回答需要依据。
如果用户问政策，系统最好能告诉你答案来自哪个文档片段，而不是凭空编。

所以 RAG 的作用是：
先从知识库里找到和问题相关的文档片段，再让大模型基于这些片段回答。

你可以把 RAG 理解成：
不是让大模型闭卷考试，而是先帮它翻资料，再让它作答。

### 2. 数据来源是什么？

你这个项目里的 RAG 数据来源主要有两类。
#### 第一类是用户上传的文档：
- .txt
- .md
- .pdf
- .docx
比如：
售后政策

退货说明

商品说明书

FAQ 文档

客服话术文档

#### 第二类是图片分析结果。

用户上传图片后，系统用智谱视觉模型分析图片。如果用户选择“写入知识库”，图片分析结果也会作为文本进入 RAG 知识库。

比如图片分析出：

图片中商品外包装有明显破损，右上角存在挤压痕迹。

这段分析结果可以被保存，后续用户问：

刚才那张图片里商品有什么问题？

系统就可以从知识库里检索到这段图片分析内容。


### 3. 文档如何进入知识库？

项目里的流程可以这样讲：

```text
用户上传文件
 ↓
后端保存文件
 ↓
计算 SHA256 文件 Hash
 ↓
检查是否重复上传
 ↓
解析文件文本
 ↓
切分成 chunk
 ↓
保存文件信息和 chunk 到数据库
 ↓
生成向量
 ↓
重建该用户的 FAISS 和 BM25 索引
```
这里有一个面试亮点：文件 Hash 去重。

也就是说，同一个文件重复上传时，系统不会重复解析、重复切分、重复向量化。

#### 你可以这样说：文档上传后，我会先计算文件 SHA256，判断这个用户是否已经上传过同一份文档。如果已经存在，就直接跳过重复索引；如果是新文档，再进入解析、切分和索引流程。这样可以减少重复计算和重复数据。

### 4. 如何切 chunk？

大模型不能每次把整篇文档都塞进去，因为：

- 文档可能太长

- 成本高

- 容易把无关内容也带进去

- 检索粒度太粗

所以要把文档切成小段，也就是 chunk。

你当前项目的默认切分方式是：
```text
chunk_size = 700
overlap = 120
意思是：
每个 chunk 大约 700 个字符
相邻 chunk 之间重叠 120 个字符
```
为什么要有 overlap？

因为如果一个完整语义刚好跨越两个 chunk，完全硬切会把上下文切断。

比如原文：

退货条件包括商品未拆封、包装完整、发票齐全。退款将在审核通过后 3-5 个工作日到账。

如果中间被切断，检索时可能只拿到前半句或后半句。

overlap 可以让相邻片段保留一部分重复上下文，降低语义断裂。

#### 面试里可以说：我使用固定窗口加 overlap 的方式切分文档，保证每个片段长度适合检索和模型输入，同时通过重叠区域减少上下文被切断的问题。

### 5. Embedding 做什么？

Embedding 就是把文本变成向量。

比如这两句话：

退款多久到账？

审核通过后 3-5 个工作日原路退回。

它们表面上没有完全相同的关键词，但语义上相关。

Embedding 模型会把它们转成向量，让语义相近的文本在向量空间里距离更近。

通俗说：
Embedding 是把文字变成机器能比较相似度的数字表示。

在你的项目里：

- 文档 chunk 会被转成向量

- 用户问题也会被转成向量

- 然后比较问题向量和 chunk 向量的距离

- 找出语义最接近的文档片段

### 6. FAISS 做什么？

FAISS 是向量检索库。

当知识库里有很多 chunk 时，如果每次都一个一个算相似度，会慢。

FAISS 的作用是：

快速从大量文本向量里找到和用户问题最相似的片段。

你的项目里使用的是 FAISS 的 IndexFlatL2。

简单解释：

- IndexFlatL2 是一种基础的向量索引

- 用 L2 距离衡量向量之间的相似度

- 数据量不大时简单可靠，适合 Demo 和简历项目

#### 面试里可以说：FAISS 主要用于 dense vector 检索，也就是语义检索。用户问题会先转成向量，然后在 FAISS 索引里找最相近的文档片段。

### 7. BM25 做什么？

BM25 是关键词检索算法。

它不像向量检索那样理解语义，而是更关注关键词匹配。

比如用户问：

订单 10001 的退货规则是什么？

这里的 10001、退货规则 这些词非常重要。

BM25 擅长处理：
- 精确关键词
- 订单号
- 型号
- 政策名称
- 专有名词
- 文档里的固定表达

你的项目里使用了：

- jieba 做中文分词
- rank-bm25 做 BM25 检索

通俗说：

FAISS 更像按意思找，BM25 更像按关键词找。

### 8. 为什么使用混合检索？

因为单独用一种检索方式都有缺点。

FAISS 向量检索的优点：

- 能理解语义相近

- 用户换一种问法也能找到相关内容

比如：退款多久到账？

能匹配到：退款将在 3-5 个工作日内原路退回。

即使没有完全相同关键词，也能找到。

但 FAISS 的缺点是：

- 对订单号、型号、专有名词可能不稳定

- 有时会找语义相近但关键词不精确的内容

- 对很短的问题可能效果不稳定

BM25 的优点：

- 精确关键词匹配强

- 对数字、编号、型号、政策名称更敏感

- 结果更可解释

但 BM25 的缺点是：

- 不理解语义

- 用户换个说法可能搜不到

比如文档写：商品签收后 7 天内可申请退货。

用户问：收到货以后多久还能退？

BM25 可能因为关键词不一致而召回弱，但向量检索能更容易找到。

所以你的项目采用混合检索：
```text
FAISS 语义检索 + BM25 关键词检索
 ↓
分数归一化
 ↓
按 0.6 * 向量分 + 0.4 * BM25 分融合
 ↓
返回 Top-K 文档片段
```
#### 面试里可以这样说：我没有只用向量检索，而是做了 FAISS + BM25 的混合检索。向量检索更适合语义相似的问题，BM25 更适合关键词、编号、型号、政策名称这种精确匹配。客服场景里既有自然语言问题，也有订单号、商品型号、政策关键词，所以混合检索能提升召回稳定性。

### 重点问题：为什么不用单纯向量检索？

这是面试高频问题。

你可以这样回答：

单纯向量检索虽然能处理语义相似的问题，但在客服场景里不够稳定。因为客服问题里经常包含订单号、商品型号、政策名称、时间规则等精确信息，这些内容对向量模型来说不一定总是排在最前面。

比如用户问“型号 X200 的耳机能不能 7 天无理由退货”，如果只做向量检索，可能会召回语义上相近的通用退货政策，但漏掉包含 X200 型号限制的具体条款。BM25 对关键词和型号更敏感，可以补上这部分能力。

所以我用了混合检索：FAISS 负责语义召回，BM25 负责关键词召回，然后对两边分数做归一化和加权融合。这样既能处理用户换一种说法的问题，也能保证关键实体和专有词不容易丢。


### RAG 完整链路面试回答

##### 如果面试官问：你的 RAG 是怎么实现的？

你可以回答：

我的 RAG 模块主要用于客服知识库问答，比如售后政策、商品说明、FAQ 文档。用户可以上传 txt、md、pdf、docx 文件，后端会先计算 SHA256 做去重，然后解析文本，把文档按固定长度加 overlap 切成 chunk，并保存文件信息和 chunk 到数据库。

索引阶段，我会用 sentence-transformers 把 chunk 转成向量，构建 FAISS 向量索引；同时用 jieba 分词后构建 BM25 关键词索引。用户提问时，系统会同时走 FAISS 语义检索和 BM25 关键词检索，对结果分数做归一化和加权融合，取 Top-K 片段作为上下文。

最后把用户问题和检索到的来源片段交给 DeepSeek 生成回答，并在页面上展示来源片段。这样可以让回答基于上传文档，降低大模型凭空编造的概率。

#### 如果面试官问：如何降低 RAG 幻觉？

你可以先简单回答，后面第七部分还会细讲：

我主要从三个方面降低幻觉：第一，回答时要求模型只基于检索片段回答，片段不足时明确说不确定；第二，前端展示来源片段，方便用户核查；第三，使用混合检索提高召回准确率，避免因为漏召回导致模型乱答。

### 你现在要理解的核心

RAG 的本质不是“向量数据库”。

RAG 的本质是：把外部知识找出来，再交给大模型回答。

你这个项目里的 RAG 亮点是：
- 文档解析
- chunk 切分
- SHA256 去重
- sentence-transformers embedding
- FAISS 语义检索
- BM25 关键词检索
- 混合召回
- 来源片段展示
