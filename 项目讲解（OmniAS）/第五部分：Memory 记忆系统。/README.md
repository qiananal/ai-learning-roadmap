## 第五部分：Memory 记忆系统。

### 1. 为什么客服 Agent 需要 Memory？

客服场景不是单轮问答，而是连续沟通。用户不会每句话都把所有信息说完整。

Memory 的价值是：让客服 Agent 能接住多轮对话，而不是每一轮都从零开始。

#### 面试里可以说：客服对话天然是多轮的，用户经常会省略上下文，所以我设计了 Memory 来保存最近对话、关键实体和长期业务状态。这样用户后续说“那”“刚才那个订单”“退款多久到账”时，系统能根据上下文继续处理。

### 2. 短期记忆解决什么问题？
短期记忆，也可以叫 Buffer Memory。它保存的是最近几轮聊天记录。短期记忆可以让模型看到最近对话，理解“那”指的是上文的订单。

你项目里的短期记忆来自数据库中的消息记录，读取最近 10 条对话。

它解决的问题是：
- 理解上下文
- 保持对话连贯
- 避免答非所问
- 让模型知道刚才聊到哪里

通俗说：短期记忆负责“刚才聊了什么”。

#### 面试回答：Buffer Memory 主要保存当前会话最近几轮消息，用来解决多轮对话里的上下文衔接问题。比如用户第二轮说“那什么时候发货”，系统可以结合上一轮查订单的对话理解用户在问哪个订单。

### 3. Entity Memory 解决什么问题？

Entity Memory 保存的是对话里抽取出来的关键实体。

比如：

- 最近订单号：last_order_no = 10001
- 待补充退货原因的订单：pending_return_order_no = 10001
- 用户最近关注的商品
- 最近使用的邮箱

它和短期记忆不一样。短期记忆是一整段聊天记录，比较散。

Entity Memory 是结构化的关键字段，更适合程序判断。

比如用户说：那帮我退货

系统不需要让大模型从十条聊天记录里猜订单号，可以直接读取：last_order_no = 10001，然后补全订单号。

通俗说：Entity Memory 负责“当前对话里最重要的业务对象是什么”。

#### 面试回答：Entity Memory 用来保存从对话中抽取出来的关键实体，比如最近订单号、待处理售后订单号等。它比纯聊天历史更稳定，因为业务流程可以直接读取这些结构化字段来补全参数。

### 4. Long-term Structured Memory 解决什么问题？

Long-term Structured Memory 保存的是更长期、更稳定的业务状态。

比如：
- 最近创建的售后单号：last_ticket_no
- 某个售后单的摘要：ticket_TKxxxx
- 用户长期偏好
- 历史售后状态

它解决的是：

- 服务重启后仍然保留状态
- 后续会话还能查到之前处理过的售后
- 页面能展示用户长期业务记录
- Agent 能知道用户之前办过什么

通俗说：Long-term Memory 负责“这个用户长期发生过什么重要业务事件”。

#### 面试回答：Long-term Structured Memory 主要保存跨会话的业务状态，比如最近售后单号、售后申请摘要等。它不是简单聊天上下文，而是持久化的结构化状态，可以支持后续继续查询和业务跟进。

### 三层记忆的区别

你可以用这个表理解：
```text
短期记忆：保存最近聊天内容。解决“刚才聊了什么”

实体记忆：保存订单号、售后单号等关键字段。解决“当前处理哪个业务对象”

长期结构化记忆：保存长期业务状态。解决“这个用户之前办过什么事情”

更口语一点：
短期记忆像聊天记录
实体记忆像便签上的关键信息
长期记忆像用户档案和业务记录
```
### 你的项目里 Memory 是怎么落地的？

当前项目里 Memory 主要通过两个地方实现。

#### 第一，最近对话记录：conversation_id -> 最近 10 条 Message 这就是 Buffer Memory。

#### 第二，用户记忆表：customer_memories

里面保存：
- user_id
- memory_type
- memory_key
- memory_value
- confidence
- source

Agent 在 load_memory 节点读取这些记忆，在 update_memory 节点写入或更新这些记忆。

### Memory 和 LangGraph 的关系
你可以这样理解：

LangGraph 是流程控制

Memory 是流程里读写的上下文数据

具体流程：
```text
load_memory
 ↓
读取短期对话和结构化记忆
 ↓
classify_intent
 ↓
结合记忆判断用户意图
 ↓
prepare_action
 ↓
用记忆补全缺失参数
 ↓
execute_tool
 ↓
执行业务操作
 ↓
update_memory
 ↓
把新的订单号、售后单号写回记忆
```
所以 Memory 不是一个孤立模块，它贯穿 Agent 流程。

### 面试回答模板：你的 Memory 怎么设计？

你可以这样回答：

我的记忆系统分成三层。第一层是短期对话记忆，保存当前会话最近几轮消息，主要用于理解上下文。第二层是实体记忆，保存订单号、待处理售后订单号这类关键字段，方便 Agent 在多轮对话里自动补全参数。第三层是长期结构化记忆，保存售后单号、售后摘要这类跨会话业务状态。

比如用户先说“帮我查订单 10001”，系统查完后会把 last_order_no=10001 写入实体记忆。下一轮用户说“那帮我退货”，虽然没有再说订单号，Agent 也可以从记忆里取出 10001，继续追问退货原因或创建售后单。

这样设计的好处是，既能保证多轮对话连续，又不会完全依赖大模型从长聊天记录里猜上下文，业务流程更可控。

### 面试官可能追问：Memory 会不会记错？

你可以回答：

会有这个风险，所以我没有把所有内容都直接写进长期记忆，而是只写业务上比较确定的结构化信息，比如订单号、售后单号。对于需要用户补充的信息，比如退货原因，系统会先追问确认。后续如果做生产级优化，我会增加记忆过期时间、置信度、用户确认机制和敏感信息过滤。

### 你现在要掌握的核心

记住这句话：短期记忆保证对话连贯，实体记忆保证参数补全，长期记忆保证业务状态可追踪。这句话非常适合面试。

还有这句话：我没有让模型完全依赖聊天历史去猜，而是把关键业务信息结构化保存下来，方便后续流程直接读取。这句话能体现工程意识。
