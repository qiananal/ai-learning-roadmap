# AI 客服 Agent 项目——面试技术问题准备

> 本文只根据当前实际使用的代码回答。每题包含直接结论、项目实现和必要的改进说明。

## 当前实现边界

当前客服 Agent 的实际流程是：

```text
加载记忆 → 识别意图 → 补全参数 → 调用工具或追问 → 更新记忆 → 生成回复
```

知识库 RAG 已经可以独立完成文档上传、混合检索和带来源回答，但目前通过 `/api/support-agent/files/ask` 单独调用，还没有成为客服 Agent 图中的节点。面试时应按这个实际情况回答。

---

## 一、项目总览

### Q1：请介绍一下这个项目

**完整回答：**

这是一个面向电商售后的智能客服系统，主要解决两类问题。

第一类是业务办理。用户可以查询订单、申请退换货或发送通知邮件。系统使用 LangGraph 编排处理流程：先读取对话记忆，再识别用户意图和参数；参数不完整时继续追问，参数完整时调用对应业务工具，最后保存记忆并生成回复。

第二类是知识问答。用户可以上传 PDF、Markdown、TXT 和 DOCX 文档。系统会进行 SHA256 去重、文本解析、分块和向量化，再结合 FAISS 语义检索与 BM25 关键词检索找到相关片段，最后让 LLM 根据片段回答并返回来源。

后端使用 FastAPI，数据访问使用异步 SQLAlchemy，默认数据库是 SQLite。当前定位是功能完整的 MVP，重点验证 Agent、RAG、工具调用和记忆管理的完整链路。

### Q2：一次客服聊天请求会经过哪些步骤？

**完整回答：**

请求进入 `POST /api/support-agent/chat` 后，主要经过以下步骤：

1. 根据用户和会话信息获取或创建 `Conversation`。
2. 把用户输入保存为一条 `Message`。
3. 调用 `support_agent_graph.ainvoke()`，并把本次请求的数据库 session 传给图。
4. `load_memory` 读取最近十条对话和用户结构化记忆。
5. `classify_intent` 判断意图并提取订单号、退货原因等参数。
6. `prepare_action` 使用记忆补全缺失参数，并判断是调用工具、继续追问还是直接回答。
7. 工具执行后，`update_memory` 保存订单号或售后结果。
8. `generate_response` 根据意图、记忆和工具结果生成最终中文回复。
9. 助手回复写入消息表，请求成功后提交事务，异常时回滚。

这个流程的重点是：LLM 负责理解语言，Python 代码负责业务约束和流程控制。

### Q3：为什么将项目分成 Agent、Service、Tool、Model 和 Schema？

**完整回答：**

这是为了让每层只负责一类事情：

- **Agent**：决定处理顺序和分支，不直接写复杂业务代码。
- **Service**：实现记忆、RAG、LLM、用户和会话等可复用能力。
- **Tool**：包装 Agent 可以执行的业务动作，例如查订单和创建售后申请。
- **Model**：定义数据库表以及表之间的关系。
- **Schema**：校验 API、工具和 LLM 输出的数据格式。

这种拆分带来三个好处：业务工具可以单独测试；更换 LLM 不需要修改数据库层；调整 Agent 流程时不需要重写订单业务。

## 二、LangGraph 与 Agent

### Q4：为什么选择 LangGraph？

**完整回答：**

这个项目不是“用户问一句，模型答一句”这么简单。一次请求中还需要读取记忆、识别意图、补参数、调用业务工具、保存结果和生成回复。LangGraph 可以把这些步骤写成独立节点，通过边和条件路由连接起来。

相比把全部逻辑写进一个大函数，LangGraph 的优势是流程清楚、节点输入输出可观察、分支可以单独测试，以后也更容易增加人工确认、重试或中断恢复。

### Q5：为什么不让大模型完全自主地选择工具和流程？

**完整回答：**

因为客服工具可能读取或修改真实业务数据。大模型适合理解“用户想做什么”，但不适合独自决定“业务条件是否满足”。

例如创建退换货申请前，必须同时有订单号和原因。项目让 LLM 提取这些信息，再由 `prepare_action` 用确定性的 Python 代码检查。缺少信息就追问，条件满足才执行工具。

这样可以降低模型幻觉造成的误操作，并让每条业务规则都能通过普通单元测试验证。

### Q6：当前 LangGraph 包含哪些节点？节点之间怎么走？

**完整回答：**

当前有七个节点：

1. `load_memory`：加载最近对话和用户记忆。
2. `classify_intent`：识别意图并抽取参数。
3. `prepare_action`：从记忆补参，并形成最终动作决定。
4. `execute_tool`：执行订单、售后或邮件工具。
5. `ask_clarification`：生成缺失参数的追问。
6. `update_memory`：保存本轮得到的重要信息。
7. `generate_response`：生成最终回复。

前三步固定执行。到 `prepare_action` 后开始分支：参数齐全且需要工具就进入 `execute_tool`；参数缺失就进入 `ask_clarification`；普通问题则直接进入 `generate_response`。工具或追问完成后会更新记忆，最后结束。

### Q7：LangGraph 的 State 是什么？为什么使用 `TypedDict(total=False)`？

**完整回答：**

State 是节点之间传递的共享数据。当前 State 保存用户 ID、会话 ID、用户消息、最近对话、结构化记忆、意图决定、工具结果、记忆更新和最终答案。

这些字段不会在流程开始时全部存在。例如 `decision` 要到意图识别后才产生，`tool_calls` 要到工具执行后才产生。因此使用 `TypedDict(total=False)`，允许节点逐步增加字段。

State 本身追求轻量；其中最关键的 `decision` 使用 Pydantic `ToolDecision`，以获得运行时数据校验。这是“外层灵活、关键数据严格”的设计。

### Q8：意图识别和参数抽取是怎么实现的？

**完整回答：**

`classify_intent` 会把三类信息放入 Prompt：当前用户消息、最近对话、已有实体和长期记忆。LLM 需要返回 `ToolDecision`，其中包含意图、订单号、退换货原因、邮箱和是否需要工具等字段。

允许的意图是查询订单、退换货、发送邮件、普通客服问题和需要追问。`LLMService.structured_chat()` 会把 Pydantic JSON Schema 告诉模型，再使用 `model_validate_json()` 校验结果。

因此这里不是简单让模型返回一段自由文本，而是要求它返回一个能够被程序继续处理的结构化对象。

### Q9：如果 LLM 超时或返回的 JSON 不合法怎么办？

**完整回答：**

代码会捕获结构化调用异常，然后执行 `fallback_decision()`。它使用关键词判断常见意图，并用正则尝试提取四位以上的订单号。

例如包含“退、换、退款”时进入退换货意图；包含“订单、物流、查”时进入订单查询意图；包含“邮件、邮箱”时进入邮件意图。

这个 fallback 的目标是保证基础可用性，而不是完全替代 LLM。它无法可靠处理复杂指代、否定句或一句话中的多个意图。生产环境还应记录 fallback 触发率，因为触发率过高通常说明模型、Prompt 或网络存在问题。

### Q10：参数补全是怎么实现的？如何避免使用错误记忆？

**完整回答：**

LLM 先从当前消息抽取参数。如果缺少订单号，`prepare_action` 会尝试使用记忆中的 `last_order_no`。如果用户正在补充退换货原因，则可以使用 `pending_return_order_no` 找到上一轮等待处理的订单。

补全后仍会检查业务所需字段：查询订单需要订单号；退换货需要订单号和原因；邮件需要邮箱、标题和正文。仍不完整时不会调用工具，而是生成明确的追问。

为了避免记忆覆盖当前指令，应遵守“当前消息中的明确值优先，记忆只补空字段”。后续还可以给临时记忆设置过期时间，避免很久以前的订单号被错误复用。

### Q11：为什么 `route_action` 使用普通 `if`，而不是再调用一次 LLM？

**完整回答：**

因为路由所需的信息已经存在于结构化 `decision` 中。代码只需判断：是否需要工具并且有工具名；是否存在追问问题；否则直接回复。

这类判断是确定性业务逻辑，不需要语言理解。使用 `if` 可以减少一次模型调用，降低延迟和费用，并保证相同 state 一定进入相同分支，也更方便写测试。

### Q12：为什么通过 `RunnableConfig` 传数据库 session？

**完整回答：**

编译后的 Graph 会被所有请求复用，但数据库 session 必须每个请求单独创建。如果把 session 放成全局变量，不同请求可能共同使用同一事务，造成数据串扰和并发错误。

API 调用 `ainvoke()` 时，把当前请求的 `db` 放入 `configurable`。需要数据库的节点再从 config 中取出它。这样整轮 Agent 调用可以共享本请求的事务，同时又与其他请求隔离。

这种方式也方便测试：测试时可以传入测试 session，而不用修改 Agent 节点代码。

### Q13：项目使用 LangGraph Checkpoint 了吗？

**完整回答：**

当前没有使用。客服图最后通过 `builder.compile()` 直接编译，没有传入 checkpointer。

Checkpoint 可以理解为“保存 LangGraph 的运行进度”。启用后，系统可以在节点执行后保存 State；如果流程暂停、服务重启或等待人工确认，可以根据同一个 `thread_id` 找回之前的 State 并继续运行。

当前项目没有使用它，是因为一次客服请求会在一个 HTTP 请求内从开始运行到结束，流程很短，不需要中途暂停。跨轮对话也不是依靠 Graph State 保存，而是显式保存在 `Message` 和 `CustomerMemory` 数据库表中，下次请求重新读取。

不使用 Checkpoint 的影响是：如果服务在图执行到一半时中断，本次图状态不能从中间节点恢复，只能重新处理整次请求。

如果以后加入“创建售后单前等待人工审核”“用户确认后继续执行”或长时间任务，就适合使用持久化 Checkpoint。具体做法是选择数据库型 checkpointer，在编译图时传入，并在每次调用 config 中提供稳定的 `thread_id`。当前 MVP 暂时不需要为了使用技术而强行加入。

## 三、业务工具与多层记忆

### Q14：当前有哪些业务工具？如何保证工具参数可靠？

**完整回答：**

当前有三个业务工具：查询订单、创建退换货申请、发送邮件。Agent 根据 `decision.tool_name` 选择对应工具。

执行前会分别构造 `QueryOrderInput`、`CreateReturnRequestInput` 或 `SendEmailInput`。这些都是 Pydantic 模型，能够检查字段是否存在、类型是否正确。也就是说，LLM 输出通过一次校验后，到工具边界还会再次转换为明确的参数对象。

工具执行结果会写入 `tool_calls`，最终回复节点根据真实结果向用户解释，不让模型自己编造订单状态或售后单号。

### Q15：工具调用失败或被重复调用时应该怎么办？

**完整回答：**

首先要区分错误类型。订单不存在属于业务错误，应直接说明；网络超时或临时数据库故障属于暂时错误，可以有限重试；未知异常要记录日志并返回安全的通用提示。

创建售后单和发送邮件会产生真实副作用，不能无条件自动重试，否则可能产生重复记录。生产化时应增加幂等机制：客户端或服务端为一次操作生成唯一 `idempotency_key`，数据库给它建立唯一约束。重复请求到达时返回第一次的结果，不再执行第二次。

项目当前还没有完整的幂等键实现，这是工具层需要补强的地方。

### Q16：三层记忆分别是什么？为什么要分层？

**完整回答：**

第一层是 Buffer Memory，即当前会话最近十条消息，用来理解“刚才说了什么”。

第二层是 Entity Memory，即结构化实体信息，例如最近订单号和正在等待补充原因的订单号，用来处理“帮我退掉刚才那个订单”这类指代。

第三层是 Long-term Memory，即需要跨会话保留的业务结果，例如最近售后单号和售后记录摘要。

分层的原因是不同信息的用途和保存时间不同。全部历史都放进 Prompt 会浪费 token 并增加噪声；只存对话文本又不方便稳定地读取订单号等关键字段。

### Q17：记忆在当前代码中如何读取和更新？

**完整回答：**

`load_memory` 使用 `MemoryService.get_buffer_memory()` 读取当前会话最近十条消息，再用 `get_user_memories()` 读取用户的结构化记忆。

`update_memory` 会把本轮识别出的订单号保存为 `last_order_no`。如果用户已经说明要退货但还没有提供原因，会保存 `pending_return_order_no`。当售后申请创建成功后，系统会清理这个临时状态，并把售后单号和完整结果保存为长期记忆。

这些更新使用 upsert：同一个 key 已存在就更新，不存在就创建。

### Q18：当前记忆实现还存在哪些问题？如何改进？

**完整回答：**

第一，临时记忆没有过期时间，较早的订单号可能在以后被错误补全。可以增加 `expires_at`，读取时忽略过期值。

第二，`get_user_memories()` 最终按 `memory_key` 生成字典。如果不同类型使用相同 key，可能发生覆盖。可以使用 `(memory_type, memory_key)` 作为完整标识，或按类型分别返回。

第三，并发请求可能同时更新同一个 key。应为 `user_id + memory_type + memory_key` 建立唯一约束，并处理并发冲突。

第四，记忆包含用户业务信息，需要权限校验、敏感字段脱敏、保存期限和用户删除能力。

### Q19：为什么 Buffer Memory 只取最近十条？

**完整回答：**

这是上下文完整度、token 成本和噪声之间的折中。最近消息通常与当前问题最相关；把全部历史发送给 LLM 会增加费用和延迟，旧话题还可能干扰当前判断。

“十条”目前是工程默认值，并不是实验得到的最优值。如果对话变长，可以采用“最近消息窗口 + 早期对话摘要”，或者只检索与当前问题相关的历史，而不是简单增加数量。

## 四、RAG 与多源文档

### Q20：完整的 RAG 入库流程是什么？

**完整回答：**

文件上传后先保存到用户目录，并计算 SHA256。系统根据 `user_id + file_hash + source_type` 查询是否已经入库，重复文件直接跳过。

未重复的文件由 `DocumentLoader` 提取文本，然后清理空行并切成有重叠的 chunk。文件元数据写入 `KnowledgeFile`，每个片段写入 `KnowledgeChunk`，同时保存 `source_label`。

之后 SentenceTransformer 批量生成向量。系统读取该用户全部 chunk，重建 FAISS 索引、metadata JSON 和 BM25 索引。

普通文档使用 `split_text()` 默认参数，即 `chunk_size=700, overlap=120`；图片分析文本才显式使用 `500/80`。

### Q21：支持哪些文件格式？各自怎么解析？

**完整回答：**

TXT 和 Markdown 使用 UTF-8 读取；PDF 使用 PyPDF2 逐页调用 `extract_text()`；DOCX 使用 python-docx 读取段落文本。

这种方案适合普通文本型文档，但存在明确边界：扫描 PDF 没有文本层，PyPDF2 可能提取不到内容；复杂表格和双栏排版可能顺序错乱；TXT 不是 UTF-8 时可能丢字符。

要改进扫描件，应增加 OCR；要处理复杂版面，应使用支持版面结构的解析工具；上传接口还应限制格式、大小和页数，并把解析失败原因写入 `index_status` 或错误字段。

### Q22：SHA256 去重是怎么实现的？有什么局限？

**完整回答：**

代码以 1 MB 为一块读取文件，不把整个大文件一次放进内存，并不断更新 SHA256，最终得到文件指纹。

它能识别“文件名不同但字节完全相同”的文件。它不能识别“内容看起来一样但文件字节不同”的情况，例如同一份 Word 重新导出为 PDF。

如果需要内容级去重，可以对提取后的文本统一空格、换行和大小写，再计算文本 SHA256。如果要识别只改动少量文字的近似重复文档，可以使用 MinHash 等方法，但复杂度更高，应根据真实重复问题决定是否加入。

### Q23：为什么要把文档切成 Chunk？为什么需要 overlap？

**完整回答：**

长文档不能直接作为一个检索单位，否则向量会混合太多主题，返回给 LLM 的上下文也会过长。因此要切成较小片段，让每个片段表达相对集中的内容。

overlap 是相邻片段重复的一部分文字，用来避免一句政策或一个步骤刚好在边界被切断。

chunk 太大，检索不够精确；太小，上下文可能不完整；overlap 太大，会产生很多重复结果。参数应通过真实问题和标注片段评估，而不是只凭经验。

### Q24：当前固定字符切块有什么不足？如何改进？

**完整回答：**

当前切分主要按字符位置，不理解标题、段落、句子和表格，因此可能把一个完整语义单元切开。

改进时可以先保留文档结构：Markdown 按标题层级切，普通文本先按段落和句子切，某一段仍过长时再按最大长度二次切分。标题和章节路径应存入 metadata，检索结果就能告诉用户具体来自哪个章节。

修改后不能只看 chunk 数量，应使用同一批问题比较 Recall@K 和答案质量，确认结构化切分确实更好。

### Q25：RAG 如何生成答案并返回来源？

**完整回答：**

`answer_question()` 先调用混合检索获得 Top-K chunk。然后把每个 chunk 的 `source_label` 和 `content` 拼接成上下文，并要求 LLM 只根据这些片段回答；资料不足时明确说“不确定”。

接口最终返回 `answer` 和 `sources`。来源中包含文件名、chunk 编号、内容和检索分数，前端可以展示引用片段。

带来源提高了可追溯性，但不等于答案一定正确。还需要检查答案中的结论是否真的由引用片段支持，这属于生成忠实度评估。

### Q26：RAG 是否已经接入客服 Agent？如果要接入，怎么做？

**完整回答：**

目前没有。知识库问答由独立的 `/files/ask` 接口处理；客服 Agent 的 `general_support` 分支不会自动调用 RAG。

要接入，需要完成以下步骤：

1. 在意图或动作决定中增加知识问答类型。
2. 给 `SupportAgentState` 增加 `retrieved_chunks` 和 `sources`。
3. 在图中新增 `retrieve_knowledge` 节点。
4. 节点使用当前请求的 db 调用 `RAGService.search()`。
5. 条件路由把知识问题送入检索节点。
6. `generate_response` 使用检索片段生成回答，API 同时返回来源。

接入后还要处理“没有命中时如何回答”和“普通闲聊不应触发检索”。这是当前代码与简历中“知识检索进入 Agent 节点流程”之间最需要补齐的地方。

## 五、Embedding、FAISS 与 BM25

### Q27：为什么同时使用 FAISS 和 BM25？

**完整回答：**

两者解决不同的匹配问题。FAISS 根据向量距离寻找语义相似内容，能匹配不同说法表达的相同意思。BM25 根据词项匹配，擅长订单号、产品型号、政策编号和专业术语。

例如“商品不想要了怎么办”和“退货申请流程”适合语义检索；“POL-2024-038”这类编号适合关键词检索。混合检索可以减少只使用一种方法造成的漏召回。

### Q28：Embedding 是什么？为什么使用当前模型？

**完整回答：**

Embedding 是把文本转换成固定长度数字向量的过程。语义越接近的文本，向量在空间中通常越接近，因此可以通过距离做语义检索。

项目配置使用 `paraphrase-multilingual-MiniLM-L12-v2`。它支持多语言，包括中文，模型规模相对适合本地 MVP。选择它是工程上的可用起点，不应声称已经通过完整横向评测证明最优。

更换 embedding 模型后必须重建全部向量索引，因为不同模型的维度或向量空间可能不同。系统还应记录索引使用的模型版本，避免新旧向量混用。

### Q29：FAISS 使用哪种索引？为什么？

**完整回答：**

当前使用 `IndexFlatL2`。它会把查询向量与索引中的所有向量计算 L2 距离，是精确搜索，不会因为近似算法漏掉候选。

它的缺点是数据越多，搜索计算量越大。当前按用户建立索引，chunk 规模较小，因此优先选择简单和准确。

数据增长后可以评估 IVF 或 HNSW。它们能提高搜索速度，但需要额外参数和召回率测试。选择时应同时比较延迟、内存和 Recall@K，而不是直接认为复杂索引一定更好。

### Q30：FAISS 的 L2 距离如何转换成可融合的分数？

**完整回答：**

FAISS 返回的 L2 距离越小越相似，而融合时希望分数越大越好。当前先使用 `1 / (1 + distance)` 转换，再对候选分数做 Min-Max 归一化。

这种方法实现简单，但归一化结果依赖当前候选集。如果最大值和最小值很接近，分数区分会不稳定。

改进前应先确认 embedding 是否做了向量归一化；如果已归一化，L2 与余弦相似度的排序存在明确关系。也可以改用内积索引，但无论使用哪种方法，都应通过同一评测集比较召回效果。

### Q31：BM25 的基本原理是什么？

**完整回答：**

BM25 根据查询词在文档中的出现情况评分。一个词在当前文档出现、同时在整个文档集合中比较少见，它的区分能力就更强。

它还处理了两个问题：同一个词重复很多次时，分数不会无限增长；长文档不会只因为包含词更多就天然占优势。

常见参数 `k1` 控制词频的饱和速度，`b` 控制文档长度归一化的强度。IDF 是根据语料统计得到的稀有程度，不是与 `k1`、`b` 相同性质的手动参数。

### Q32：中文 BM25 为什么需要 jieba？

**完整回答：**

BM25 的基本单位是词。英文可以按空格分词，中文句子没有天然空格，因此项目使用 `jieba.lcut()` 把文本和查询切成词，再进行小写和空白清理。

通用分词器可能把产品型号、售后术语和政策编号切错。可以收集真实业务词建立自定义词典，并比较加入前后的查询命中情况。不能只看分词结果是否“像人话”，最终要看检索效果是否提高。

### Q33：FAISS 和 BM25 的结果是如何融合的？

**完整回答：**

查询时，系统先从 FAISS 取 `top_k * 3` 个稠密候选，同时计算 BM25 分数。两路分数分别归一化，再按照同一个 chunk 的索引合并。

最终分数为 `0.6 × dense_score + 0.4 × bm25_score`，按总分降序返回 Top-K。语义检索权重稍高，同时保留关键词检索贡献。

0.6/0.4 是当前工程初始值，仓库没有实验可以证明它最优。正确调法是准备带相关片段标注的问题集，比较不同权重下的 Recall@K、MRR 或 nDCG。

### Q34：什么是 RRF？为什么它适合混合检索？

**完整回答：**

FAISS 和 BM25 的原始分数含义不同，直接相加前需要归一化。RRF 的思路是不比较原始分数，只看同一文档在每一路结果中排第几。

每一路可以按 `1 / (k + rank)` 给文档加分，通常 `k` 取一个固定常数。一个 chunk 如果在两路都排得靠前，总分就会更高。

要在项目中使用，可以保留两路排序结果，以 chunk ID 合并排名并计算 RRF 分数。然后在同一标注集上与当前线性加权比较。RRF 更容易避免分数量纲问题，但不代表一定优于经过充分调参的线性融合。

### Q35：索引如何持久化？如何保证三份数据一致？

**完整回答：**

FAISS 索引保存为用户级 `.faiss` 文件；向量位置对应的 chunk 信息保存为 JSON；BM25 对象保存为 pickle；原始文件和 chunk 记录保存在文件系统与 SQLite。

当前每次新增文档后，会从数据库读取该用户全部 chunk，并整体重建三份索引。这种方式在小规模下简单，但数据变大后重建时间会明显增加。

还存在一致性风险：如果写完 FAISS 后写 JSON 失败，三份文件可能不匹配。改进方法是在临时目录完成全部构建和校验，成功后再原子替换旧文件；同时用版本号标记同一批索引。重建任务也应放到后台 Worker，避免阻塞请求。

### Q36：如何评估 RAG 效果？

**完整回答：**

评估要分成检索和生成两层。

检索层检查正确片段是否进入 Top-K。Recall@K 表示正确片段是否被前 K 个结果覆盖；MRR 更关注第一个正确结果排得是否靠前；nDCG 可以考虑多个相关结果的排名质量。

生成层检查回答是否正确、是否只依据提供的片段、引用是否真的支持结论、没有资料时能否正确拒答。

落地时应准备一批真实客服问题，为每题标记相关 chunk 和参考答案。修改 embedding、chunk、Top-K 或融合权重后自动重跑，才能知道改动是提升还是退步。

## 六、FastAPI、Pydantic 与数据库

### Q37：为什么使用 FastAPI？

**完整回答：**

项目需要等待 LLM 请求、LangGraph 节点和异步数据库操作，FastAPI 基于 ASGI，适合使用 `async/await` 处理这类 I/O 等待。

它还与 Pydantic 深度集成，可以自动校验请求参数、生成响应结构和 OpenAPI 文档，前端与测试人员可以直接使用 `/docs`。

需要注意，`async def` 只对异步 I/O 有帮助；CPU 计算和同步文件操作仍可能阻塞事件循环。

### Q38：当前哪些操作可能阻塞事件循环？如何改？

**完整回答：**

SentenceTransformer 编码、FAISS 重建、PDF/DOCX 解析、同步文件读写和 pickle 序列化都不是异步网络 I/O。文件较大时，直接在接口内执行会占住服务线程，使其他请求等待。

简单改法是把较短的同步工作放入线程池。更可靠的方案是：上传接口只保存文件并创建 `pending` 任务，后台 Worker 负责解析、embedding 和建索引，完成后把状态更新为 `indexed`，失败则标记 `failed`。前端通过任务 ID 查询状态。

FastAPI `BackgroundTasks` 适合单机轻量任务；需要持久重试、多进程或任务监控时，应使用 Celery、RQ 等独立队列。

### Q39：`Depends(get_db)` 如何管理数据库 session 和事务？

**完整回答：**

每个请求进入时，`get_db()` 创建一个 `AsyncSessionLocal`。路由和 Agent 节点共享这一个 session。业务正常返回后，控制流回到 `yield` 后执行 `commit`；发生异常时执行 `rollback`；最后关闭 session。

Service 中通常使用 `flush`，让 SQL 发到数据库并获得主键，但不提前结束事务。最终由请求级依赖统一提交，可以保证一轮业务要么整体成功，要么整体回滚。

当前个别路由仍显式调用 `commit`，后续应统一事务边界，避免一部分数据提前提交后后续步骤失败。

### Q40：项目使用 Pydantic v1 还是 v2？Pydantic 用在哪里？

**完整回答：**

当前代码实际使用 Pydantic v2，因为调用了 `model_validate_json()`、`model_json_schema()` 和 `model_dump()`，并使用 `pydantic-settings` v2 管理配置。

Pydantic 有三类用途：校验 FastAPI 请求和响应；校验业务工具参数；校验 LLM 返回的结构化 JSON。

`requirements.txt` 当前写的是 `pydantic>=1.8.0`，与实际代码不一致，应改成兼容 v2 的下限，例如 `pydantic>=2.0.0`，并通过锁定依赖或测试保证版本稳定。

### Q41：为什么默认使用 SQLite？生产环境能继续用吗？

**完整回答：**

SQLite 是单文件数据库，不需要安装和维护独立服务，很适合本地演示和 MVP。配合 `aiosqlite`，项目可以继续使用 SQLAlchemy 异步接口。

它的主要限制是并发写入能力较弱，不适合大量用户同时写订单、消息和记忆。生产环境通常会迁移到 MySQL 或 PostgreSQL。

项目配置虽然已经支持 MySQL URL，但真正迁移还需要数据库建表与迁移脚本、连接池配置、数据迁移、SQL 兼容性和并发测试，不能简单说只改一行配置。

### Q42：异步 SQLAlchemy 常见问题有哪些？

**完整回答：**

第一，AsyncSession 不是可以随意跨并发任务共享的全局对象，应按请求创建。

第二，`flush` 只把变更发送到数据库，事务仍可回滚；`commit` 才是正式提交。

第三，异步环境应避免访问未加载关系时触发隐式懒加载。需要关联数据时应提前使用 eager loading。集合关系常用 `selectinload`；`joinedload` 也能避免 N+1，但连接集合时可能产生重复行。

第四，异常路径必须回滚，事务边界要统一；并发修改同一记录时还需要唯一约束、锁或版本控制。

## 七、可靠性、安全与系统设计

### Q43：项目如何减少 LLM 幻觉？

**完整回答：**

首先，订单状态和售后结果必须来自业务工具，不能让 LLM 自己生成。其次，工具参数和结构化输出使用 Pydantic 校验。再次，RAG Prompt 要求模型只根据检索片段回答，资料不足时明确说明不确定。

这些措施分别约束事实来源、数据格式和回答依据。进一步可以增加引用一致性检查、意图与参数评测、高风险操作的用户确认，以及对 Prompt 和模型版本的回归测试。

### Q44：如何防止重复创建售后单？

**完整回答：**

需要幂等机制。幂等表示同一个业务请求即使重复发送，最终也只产生一次结果。

具体做法是为创建请求生成 `idempotency_key`，并在数据库建立唯一约束。事务中先根据 key 查询；已存在就返回原售后单，不存在才创建。唯一约束还能防止两个并发请求同时通过查询后各自创建一条记录。

如果暂时没有独立 key，也可以根据用户、订单、请求类型和未结束状态设计业务唯一约束，但独立幂等键通常更清晰。

### Q45：当前用户知识库如何隔离？还缺什么？

**完整回答：**

当前知识文件、chunk 查询、上传目录和索引文件都按 `user_id` 隔离，例如每个用户有自己的 FAISS 文件。

但数据隔离不只是在路径中加入用户 ID。接口必须从登录 token 中取得当前用户身份，并在数据库查询中强制使用该 ID，不能完全相信请求体传来的 `user_id`。否则攻击者可能修改参数访问其他用户数据。

还应检查文件和会话资源的所有权，并为越权访问返回统一的 403 或 404。

### Q46：文件上传有哪些安全风险？

**完整回答：**

需要限制扩展名、MIME 类型、文件大小、PDF 页数和单用户配额；保存时使用服务生成的安全文件名，防止 `../` 路径穿越；解析任务要设置超时和内存限制，避免恶意大文件拖垮服务。

必要时增加恶意文件扫描，并把解析放到隔离 Worker。系统内部使用的 pickle 只能加载服务自己生成的文件，绝不能把用户上传的 pickle 直接反序列化，因为恶意 pickle 可能执行代码。

### Q47：如何增加日志、监控和问题排查能力？

**完整回答：**

每次请求应生成 request ID，并记录会话 ID、各 LangGraph 节点耗时、LLM 模型与调用耗时、是否触发 fallback、工具名称与结果状态、检索来源与分数、异常类型。

关键指标包括接口成功率和延迟、LLM 错误率、fallback 比例、工具失败率、文档索引耗时和无检索结果比例。

日志不能直接记录完整邮箱、订单详情和用户文档。进一步可以接入 OpenTelemetry，把 FastAPI、LangGraph、LLM 和数据库调用关联成一条 trace。

### Q48：用户量和文档量增加后，系统如何扩展？

**完整回答：**

API 层应尽量无状态，才能部署多个实例；业务数据迁移到 MySQL/PostgreSQL；文档解析、embedding 和索引构建放入任务队列，由 Worker 异步执行；模型调用增加超时、有限重试、限流和熔断。

当前用户级 FAISS 适合小规模。数据显著增长后，可以先优化增量索引和缓存；当需要分布式存储、复杂 metadata 过滤和高可用时，再评估专门的向量数据库。

扩展应由实际瓶颈驱动，不需要在 MVP 阶段一次引入所有复杂组件。

### Q49：如果继续开发，最优先改哪三点？

**完整回答：**

第一，把 RAG 封装成客服 LangGraph 的知识检索节点，让知识问题能够在主流程中自动检索并返回来源。这也能使代码与简历描述完全一致。

第二，把文档解析、embedding 和索引重建移到后台任务，增加任务状态与失败重试，避免大文件阻塞接口。

第三，补齐质量和安全保障：建立 RAG 与意图识别评测集，为创建售后单增加幂等约束，并完善用户权限和监控。

这三个改进分别解决能力闭环、性能和生产可靠性问题，优先级高于单纯增加更多模型或框架。
