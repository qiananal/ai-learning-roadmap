# AI 客服 Agent 项目——面试技术问题准备

> 根据当前实际代码和简历技术点整理。每题先给出容易记的回答，再补充代码细节。标注“怎么改”的内容是后续方案，不要说成已经实现。

## 回答前先记住一个边界

当前客服入口使用 `app/lg_agent/support_agent_builder.py`，流程是：

```text
加载记忆 → 判断意图 → 补充参数 → 调用工具/继续追问 → 更新记忆 → 生成回复
```

知识库 RAG 已经完整实现，但现在通过独立接口 `/api/support-agent/files/ask` 使用，还没有接入上述 Agent 主流程。旧版 `lg_builder.py`、GraphRAG 和图片分析属于扩展或实验代码。

## 一、项目总览

### Q1：请简单介绍一下这个项目

**回答：**

这是一个电商售后客服系统，主要有两部分。

第一部分是客服 Agent：它能理解用户是要查订单、退换货还是发邮件；参数不完整时继续追问，完整时调用业务工具，并保存对话记忆。

第二部分是知识库 RAG：用户可以上传 PDF、Markdown、TXT、DOCX，系统会提取文字、切分、建立 FAISS 和 BM25 索引，然后根据文档内容回答问题并返回来源片段。

整个后端使用 FastAPI，流程编排使用 LangGraph，数据默认保存在 SQLite。

### Q2：一次客服请求会经过哪些步骤？

**回答：**

可以记成六步：**存消息、读记忆、判意图、补参数、调工具、写结果**。

具体来说，接口先保存用户消息，然后 LangGraph 读取最近对话和用户记忆。LLM 判断意图并提取订单号等参数；缺少参数就追问，参数完整就调用工具。最后更新记忆、生成回复并保存助手消息。

数据库操作使用同一次请求的 `AsyncSession`，请求成功后统一提交，失败时回滚。

### Q3：项目为什么要分成 Agent、Service、Tool 和 Model？

**回答：**

因为它们负责的事情不同：

- Agent 决定先做什么、后做什么。
- Service 实现记忆、RAG、LLM 等通用能力。
- Tool 实现查询订单、创建售后单等业务动作。
- Model 和 Schema 负责数据库结构与数据校验。

这样改业务工具时不用重写整个流程，测试某个功能时也可以单独测试。

## 二、LangGraph 与 Agent

### Q4：为什么选择 LangGraph？

**回答：**

因为客服不是只问一次大模型，而是要经过读取记忆、判断意图、补参数、调用工具和保存结果等多个步骤。LangGraph 可以把每一步写成节点，再用边连接起来，代码更清楚，出错时也容易找到具体节点。

可以把它理解为一张可以运行的客服流程图。

### Q5：为什么不让大模型完全自由地决定流程？

**回答：**

售后操作会修改真实业务数据，不能全部相信模型。例如没有订单号和原因时，系统不应该直接创建退货申请。

所以项目让 LLM 负责理解自然语言，让普通 Python 代码负责检查参数和选择分支。这样既利用了模型的理解能力，又能保证业务规则稳定。

### Q6：当前 LangGraph 有哪些节点？

**回答：**

一共有七个节点：

1. `load_memory`：读取最近对话和用户记忆。
2. `classify_intent`：判断用户意图并提取参数。
3. `prepare_action`：利用记忆补参数。
4. `execute_tool`：调用业务工具。
5. `ask_clarification`：向用户追问缺少的信息。
6. `update_memory`：保存订单号和售后结果。
7. `generate_response`：生成最终回复。

`prepare_action` 后会根据情况走不同分支，所以它不是一条完全固定的直线。

### Q7：LangGraph 的 State 是什么？为什么使用 `TypedDict`？

**回答：**

State 是所有节点共用的一份数据，可以简单理解成一个字典。里面保存用户 ID、消息、记忆、意图、工具结果和最终答案。

不同字段是在不同节点逐步加入的，所以代码使用 `TypedDict(total=False)`，表示字段不需要一开始全部存在。需要严格检查的 `decision` 字段则使用 Pydantic 模型。

### Q8：意图识别和参数提取是怎么做的？

**回答：**

系统把用户消息、最近对话和已有记忆一起发给 LLM，让它返回固定格式的 `ToolDecision`。

当前意图包括查订单、退换货、发邮件、普通客服问题和需要继续追问。返回结果还可以包含订单号、退换货原因、邮箱等字段。

为了避免模型随便输出，代码先把 Pydantic 定义的数据格式告诉模型，再用 `model_validate_json()` 检查返回的 JSON。

### Q9：如果 LLM 返回错误格式怎么办？

**回答：**

项目有一个简单的兜底方法 `fallback_decision()`。当 LLM 超时或 JSON 不合法时，它会用关键词和正则判断常见意图，并尝试提取订单号。

例如消息里有“退货”就判断为退换货，有“订单”或“物流”就判断为查询订单。

这个方法只能处理简单情况，作用是防止接口直接报错，不是用来代替 LLM。

### Q10：参数补全是怎么做的？

**回答：**

如果当前消息没有订单号，系统会查看记忆中的 `last_order_no`。例如用户上一轮说“查订单 12345”，下一轮只说“帮我退掉”，系统可以自动补上 12345。

如果记忆中也没有，就设置一个追问，例如“请提供订单号”。原则是：用户这次明确输入的内容优先，记忆只用于补充缺失字段。

### Q11：`route_action` 为什么不用 LLM？

**回答：**

因为路由只需要看已经得到的三个结果：是否需要工具、有没有工具名、是否需要追问。

这些都是明确的真假判断，用 `if` 就能完成。这样少调用一次 LLM，速度更快、成本更低，而且相同输入一定会走相同分支。

### Q12：为什么通过 `RunnableConfig` 传数据库 session？

**回答：**

LangGraph 对象会被很多请求共同使用，但每个请求必须有自己的数据库 session。API 调用图时把当前 `db` 放进 config，节点需要数据库时再取出来。

这样不会把一个全局 session 错误地交给多个用户共同使用，测试时也可以传入测试数据库。

### Q13：项目使用 LangGraph Checkpoint 了吗？

**回答：**

当前客服主图没有使用。跨轮对话依靠 `Message` 和 `CustomerMemory` 表保存。

旧版 `lg_builder.py` 使用过内存版 `MemorySaver`，但重启后会丢失。如果以后需要人工审核或暂停后继续执行，可以给当前主图增加持久化 checkpointer，并用会话 ID 区分不同用户流程。

**具体怎么改：**编译图时传入 SQLite 或数据库 checkpointer；调用图时在 config 中增加稳定的 `thread_id`。这样系统才能找到同一条流程之前保存的状态。

## 三、业务工具与多层记忆

### Q14：项目有哪些业务工具？

**回答：**

当前主要有三个工具：查询订单、创建退换货申请、发送邮件。

调用工具前会先构造对应的 Pydantic 参数对象。也就是说，即使参数来自 LLM，也必须再检查一次，不能直接把模型生成的文本写入业务系统。

### Q15：工具调用失败应该怎么处理？

**回答：**

首先要区分错误类型。网络超时可以重试；订单不存在不能重试，应该直接告诉用户；创建售后单和发送邮件属于会产生真实结果的操作，还要防止重复执行。

**具体怎么改：**给创建售后单请求增加一个唯一请求号 `idempotency_key`，数据库给它加唯一约束。同一个请求再次到达时，直接返回原来的售后单，不再新建。幂等的简单意思就是“重复请求只生效一次”。

### Q16：什么是三层记忆？

**回答：**

- 短期记忆：当前会话最近十条消息。
- 实体记忆：订单号、待处理订单号等关键字段。
- 长期记忆：已经创建的售后单等长期业务结果。

短期记忆让模型知道刚才聊了什么，实体记忆帮助补参数，长期记忆用于跨会话追踪业务结果。

### Q17：三层记忆在代码中如何读写？

**回答：**

`load_memory` 调用 `MemoryService` 读取最近消息和用户记忆。订单号会被保存为实体记忆；创建售后单成功后，会保存售后单编号和完整结果，并清理“等待补充原因”等临时状态。

这些修改使用同一个请求的数据库事务，正常结束后一起提交。

### Q18：当前记忆设计有什么问题？

**回答：**

主要有四点：旧订单号可能被错误复用；记忆没有过期时间；并发请求可能同时修改同一个字段；记忆中还可能包含用户隐私。

**具体怎么改：**给临时记忆增加过期时间；明确“当前消息优先于历史记忆”；为用户 ID、记忆类型和 key 建立唯一约束；敏感字段做脱敏并提供删除接口。

### Q19：为什么短期记忆只取最近十条？

**回答：**

历史消息越多，消耗的 token 越多，而且旧话题可能干扰当前问题。十条是当前项目的简单折中。

如果以后对话很长，可以保留最近消息，再把更早的内容总结成一段摘要，而不是把全部历史都发给模型。

## 四、知识库 RAG 与多源文档

### Q20：完整的 RAG 入库流程是什么？

**回答：**

可以记成：**去重、解析、切块、向量化、建索引**。

文件上传后，系统先计算 SHA256 判断是否重复，再提取文字并切成小段。每个小段写入数据库并生成向量，最后建立 FAISS 向量索引和 BM25 关键词索引。

普通文档实际使用 `chunk_size=700, overlap=120`；图片分析文本使用 `500/80`，不要混在一起回答。

### Q21：支持哪些文件格式？怎么解析？

**回答：**

TXT 和 Markdown 直接读取文字；PDF 使用 PyPDF2 逐页提取；DOCX 使用 python-docx 提取段落。

当前方法对扫描版 PDF、复杂表格和双栏文档效果不好，因为这些文件不一定包含正常的文字顺序。

**具体怎么改：**扫描件先用 OCR 识别；表格或复杂 PDF 使用带版面分析的解析工具；上传时限制文件大小、页数和格式，解析失败要记录原因。

### Q22：SHA256 去重怎么实现？

**回答：**

系统分块读取文件并计算 SHA256。即使文件改了名字，只要字节内容完全相同，哈希就相同，会被识别为重复文件。

如果同一份内容重新导出成另一个 PDF，字节可能变化，SHA256 就识别不出来。

**具体怎么改：**先提取文字、去掉多余空格和换行，再对清理后的文本计算哈希。需要判断“内容大致相同”时，可以进一步使用 MinHash，但当前项目还没有实现。

### Q23：为什么文档切块需要 overlap？

**回答：**

因为一句重要内容可能刚好被切成两半。相邻块保留一部分重复文字，可以让边界附近的信息在至少一个块中保持完整。

重叠太大也不好，会增加索引数量，还可能让相似的相邻块占满搜索结果，所以要用真实文档测试。

### Q24：当前切块方式有什么不足？

**回答：**

现在主要按字符数切，可能把标题、句子或表格拆开，不理解文档结构。

**具体怎么改：**Markdown 先按标题切，普通文档先按段落和句号切；某一段仍然太长时再按最大长度切。还可以把标题保存到 metadata 中，让检索结果带上章节信息。

### Q25：RAG 如何返回来源？

**回答：**

每个 chunk 都保存一个 `source_label`，例如“退款政策.pdf #chunk-3”。搜索后，系统把命中的内容和来源一起交给 LLM，也把 `sources` 返回给前端。

Prompt 要求资料不足时回答“不确定”。但返回了来源不代表答案一定正确，还要检查答案是否真的得到来源片段支持。

### Q26：RAG 已经接入 LangGraph 主流程了吗？

**回答：**

目前没有。客服 Agent 和知识库问答都已经实现，但还是两个独立入口。

**具体怎么改：**

1. 给 state 增加 `retrieved_chunks` 和 `sources`。
2. 增加知识问答意图。
3. 在 `support_agent_builder.py` 新增 `retrieve_knowledge` 节点。
4. 节点中调用 `RAGService.search()`。
5. 检索后进入 `generate_response`，并把来源一起返回。

这也是让当前代码与简历中“知识检索进入节点化流程”完全一致的关键改进。

## 五、FAISS、Embedding 与 BM25

### Q27：为什么同时使用 FAISS 和 BM25？

**回答：**

FAISS 擅长找“意思相近”的内容，BM25 擅长找“关键词完全命中”的内容。

例如“怎么退掉不想要的商品”和“退货流程”意思接近，FAISS 更有优势；订单号、产品型号、政策编号需要准确匹配，BM25 更有优势。两者合起来可以互相补充。

### Q28：Embedding 是什么？为什么选择当前模型？

**回答：**

Embedding 就是把一段文字变成一串数字。意思接近的文字，数字之间的距离通常也更近。

项目使用 `paraphrase-multilingual-MiniLM-L12-v2`，因为它支持包括中文在内的多种语言，模型规模也比较适合本地 MVP。

如果更换模型，需要重新生成全部向量和索引，因为不同模型产生的数字空间不能直接混用。

### Q29：FAISS 使用哪种索引？为什么？

**回答：**

项目使用 `IndexFlatL2`。它会和所有向量逐个比较，结果准确、实现简单，适合当前每个用户数据量不大的情况。

数据量很大时，可以测试 IVF 或 HNSW。它们通过近似搜索提高速度，但可能漏掉少量正确结果。不能只凭名字选择，要比较搜索速度、内存和召回率。

### Q30：L2 距离如何变成相似度分数？

**回答：**

FAISS 返回的距离越小越相似。当前代码先计算 `1 / (1 + distance)`，把它变成越大越相似的分数，然后再归一化到相近范围。

这种做法简单，但分数会受本次候选结果影响。如果要改，应该先保证向量是否归一化，再在测试集上比较 L2、内积或 cosine 的效果。

### Q31：BM25 的原理是什么？

**回答：**

可以理解成一种更合理的关键词计分方法。某个词在当前文档中出现，同时在其他文档中比较少见，它的作用就更大。

`k1` 控制一个词重复出现多少次后不再明显加分，`b` 控制是否照顾长短不同的文档。面试中说明这两个参数即可。

### Q32：中文 BM25 为什么需要 jieba？

**回答：**

英文单词之间有空格，中文没有。BM25 必须先知道哪些字组成一个词，所以项目使用 jieba 分词。

如果商品型号或售后术语经常被切错，可以把这些词加入 jieba 自定义词典，然后用实际查询测试命中率是否提高。

### Q33：FAISS 和 BM25 的结果怎么融合？

**回答：**

系统先分别得到两组候选结果，再把两组分数归一化，然后按 chunk 合并。最终分数是：

```text
0.6 × FAISS 分数 + 0.4 × BM25 分数
```

0.6/0.4 只是目前的初始经验值，仓库中没有实验能证明它最好。

**具体怎么改：**准备一批问题并人工标记正确片段，分别测试 0.5/0.5、0.6/0.4、0.7/0.3，比较正确片段进入前几名的比例，再决定权重。

### Q34：RRF 是什么？为什么可以用它融合结果？

**回答：**

RRF 不直接比较 FAISS 和 BM25 的原始分数，只看一个文档在两组结果中分别排第几。排名越靠前，加分越多。

**具体怎么改：**分别保留两组排名，同一个 chunk 每一路按 `1 / (60 + 排名)` 加分，最后按总分排序。然后把结果和当前 0.6/0.4 方法放在同一测试集上比较。它只是备选方法，不一定绝对更好。

### Q35：索引如何保存？如何避免数据不一致？

**回答：**

FAISS 保存为 `.faiss` 文件，chunk 信息保存为 JSON，BM25 对象保存为 pickle，原始 chunk 同时保存在 SQLite。

当前新增文档时会重新读取该用户的全部 chunk，并重建三份索引。数据小时简单可靠，数据大时会变慢。

**具体怎么改：**先在临时路径建立三份新索引，全部成功后再一次性替换旧文件。这样中途失败不会留下“一半新、一半旧”的索引。重任务还可以放到后台 Worker 执行。

### Q36：如何判断 RAG 效果好不好？

**回答：**

不能只看最终回答“感觉不错”，要分两步检查。

第一步看检索：正确文档片段有没有进入前 K 名。第二步看生成：已经找到正确片段后，模型有没有按照片段回答，有没有引用错误。

**具体怎么改：**准备 30～100 个真实问题，为每题标记正确片段和参考答案。每次修改 chunk、权重或模型后都重新跑一遍，记录 Recall@K、MRR 和答案正确率。简单理解：Recall@K 看正确片段有没有被找到，MRR 看它排得够不够靠前。

## 六、FastAPI、Pydantic 与数据库

### Q37：为什么选择 FastAPI？

**回答：**

项目需要等待 LLM、LangGraph 和数据库等 I/O 操作，FastAPI 对 `async/await` 支持很好；它还能结合 Pydantic 自动校验参数并生成 `/docs` 接口文档。

但函数写成 `async def` 不代表里面所有工作都会自动变成非阻塞。

### Q38：哪些操作可能阻塞 FastAPI？

**回答：**

Embedding 计算、FAISS 建索引、PDF 解析和同步文件读写都可能占用较长时间。它们直接放在异步接口中，会让其他请求等待。

**具体怎么改：**上传接口先保存文件并返回任务 ID；后台 Worker 再解析和建索引；数据库记录 `pending/indexed/failed` 状态，前端通过任务 ID 查询进度。小型 MVP 可先用 `BackgroundTasks`，需要重试和多进程时再用 Celery 或 RQ。

### Q39：`Depends(get_db)` 如何管理数据库 session？

**回答：**

每个请求创建一个自己的 `AsyncSession`。业务成功后执行 `commit`，发生异常时执行 `rollback`，最后关闭 session。

Agent 中的多个节点通过 `RunnableConfig` 共享本次请求的 session。Service 层最好只调用 `flush`，把最终是否提交交给请求层统一决定。

### Q40：项目使用 Pydantic v1 还是 v2？

**回答：**

实际代码使用 v2，因为用到了 `model_validate_json()`、`model_json_schema()` 和 `model_dump()`。

Pydantic 在项目中有三个作用：检查 API 参数、检查工具参数、检查 LLM 返回的 JSON。`requirements.txt` 中 `pydantic>=1.8.0` 的下限与代码不一致，后续应该改为 `pydantic>=2.0.0`。

### Q41：为什么默认使用 SQLite？

**回答：**

SQLite 不需要安装单独的数据库服务，适合本地演示和 MVP。它的并发写入能力有限，不适合大量用户同时操作。

项目配置已经支持 MySQL，但正式迁移还要做建表迁移、连接池配置和并发测试，不是只修改一个数据库地址。

### Q42：异步 SQLAlchemy 容易遇到哪些问题？

**回答：**

要记住三点：一个请求使用自己的 session；`flush` 不等于 `commit`；需要关联数据时提前加载，不要在异步环境中随意触发懒加载。

集合关系常用 `selectinload`，`joinedload` 也能避免 N+1，但可能生成很多重复行。两者要按查询关系选择，而不是固定只用其中一个。

## 七、可靠性、安全与深入追问

### Q43：如何减少 LLM 幻觉？

**回答：**

模型不能作为事实来源。订单状态以数据库工具结果为准，知识问答以检索到的文档为准，参数还要经过 Pydantic 检查。资料不足时应该回答不知道，而不是编造。

进一步可以增加引用检查和测试集；创建售后单等高风险操作还可以要求用户确认。

### Q44：如何防止重复创建售后单？

**回答：**

使用幂等机制，也就是同一个请求重复发送只产生一条结果。

**具体怎么改：**请求带唯一 `idempotency_key`，售后表给这个字段增加唯一约束。创建前先查询，存在就返回原记录；不存在才创建，并把查询与创建放在同一个事务中。

### Q45：如何隔离不同用户的知识库？

**回答：**

当前数据库查询、上传目录和索引文件都带 `user_id`。但仅在路径中带 ID 还不够，接口不能完全相信请求体传来的用户 ID。

**具体怎么改：**从登录 token 中获取当前用户 ID，并在每次数据库查询中使用它；如果请求中的资源不属于当前用户就拒绝访问。

### Q46：文件上传需要注意哪些安全问题？

**回答：**

要限制文件格式、大小和页数，使用安全文件名，防止路径穿越，并给解析任务设置超时和内存限制。

pickle 只能加载系统自己生成的文件，不能反序列化用户上传的 pickle，因为恶意 pickle 可能执行代码。

### Q47：项目如何增加日志和监控？

**回答：**

每次请求应该记录请求 ID、会话 ID、每个节点耗时、模型名称、工具调用结果、检索来源和异常类型。

日志不能直接记录完整邮箱、订单信息和用户隐私。进一步可以使用 OpenTelemetry，把 FastAPI、LangGraph、LLM 和数据库调用串成一条完整链路。

### Q48：用户和文档数量增加后如何扩展？

**回答：**

先把 API 服务做成无状态多实例；业务数据库迁移到 MySQL/PostgreSQL；文档解析和建索引放入任务队列；模型调用增加超时、重试和限流。

FAISS 适合当前小规模用户级索引。数据非常大、需要分布式和复杂过滤时，再考虑专门的向量数据库，不需要一开始就把系统设计得过重。

### Q49：如果继续开发，最优先改哪三点？

**回答：**

第一，把 RAG 做成 LangGraph 的知识检索节点，让简历描述和主流程完全一致。

第二，把文档解析和索引构建放到后台任务，避免上传接口长时间卡住。

第三，建立测试集并为创建售后单增加幂等控制，同时解决“效果能否证明”和“重复操作是否安全”两个问题。
