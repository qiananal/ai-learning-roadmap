## 第二部分：系统架构分析

这一部分要建立一个整体地图：这个项目不是“一个大模型聊天页面”，而是由前端、后端、Agent、数据库、RAG、Memory、LLM 服务几部分配合起来的。

### 1. 前端负责什么？
前端就是用户看到的页面。

它主要负责：

- 展示聊天窗口

- 接收用户输入

- 把用户消息发给后端 API

- 展示 AI 回复

- 展示订单数据

- 展示售后单数据

- 展示记忆状态

- 上传文件做文档问答

- 上传图片做图片理解

- 展示 Agent 的执行过程，比如识别到的意图、调用了什么能力、更新了哪些记忆

你可以把前端理解成：

前端不负责真正的智能决策，它负责把用户操作变成请求，再把后端结果可视化展示出来。

#### 面试里可以说：

前端主要承担交互和可视化，把聊天、订单、售后、记忆、文档问答和图片理解这些能力整合到一个演示页面里。

### 2. 后端负责什么？

后端是整个系统的核心调度层。

它负责：

- 接收前端请求

- 暴露 API 接口

- 调用 Agent 流程

- 调用数据库查询订单、售后、记忆

- 调用 DeepSeek 生成自然语言回复

- 调用智谱视觉模型分析图片

- 管理文档上传、切分、向量化和检索

- 把最终结果返回给前端

你可以理解为：

后端是系统的大脑和中控台，所有真实业务逻辑都在后端发生。

### 3. Agent 负责什么？

Agent 负责“像客服一样思考和行动”。

普通聊天机器人只会回答一句话，而 Agent 会先判断：

用户是要查订单？还是要申请退货？还是问售后政策？是否缺少订单号？是否可以从历史记忆里补全订单号？是否需要查数据库？是否需要创建售后单？是否需要更新记忆？最后应该怎么组织客服回复？

所以 Agent 的职责不是简单生成文本，而是：

理解用户意图，决定下一步动作，调用业务能力，最后生成符合客服语气的回复。

#### 面试里可以说：

Agent 是业务决策层，它负责把用户自然语言转成具体的客服流程，比如查订单、创建售后、读取记忆、更新记忆等。

### 4. LangGraph 在其中的位置？

LangGraph 是 Agent 流程的编排框架。

你可以把 LangGraph 理解成一张“客服处理流程图”。

比如一次用户请求进来，不是直接丢给大模型，而是按照流程走：

```text
加载记忆
 ↓
识别意图
 ↓
补全参数
 ↓
判断是否需要业务操作
 ↓
执行查询订单 / 创建售后 / 发送邮件
 ↓
更新记忆
 ↓
生成最终回复
```
LangGraph 的作用就是把这些步骤拆成节点，并控制节点之间怎么流转。

#### 面试里不要说得太玄，可以这样讲：

我使用 LangGraph 是为了把客服 Agent 的多步处理过程显式管理起来。相比直接写一个很长的 prompt，它可以把记忆读取、意图判断、业务处理、回复生成拆成不同节点，流程更清楚，也更容易调试。

### 5. RAG 模块在哪里？

RAG 模块负责“文档问答”。

比如你上传一份售后政策 PDF，然后问：

7天无理由退货规则是什么？

系统不应该只靠大模型自己的训练知识回答，因为那些知识可能不准确，也不知道你上传的具体文档内容。
所以 RAG 的流程是：

```text
上传文档
 ↓
解析文本
 ↓
切成小段 chunk
 ↓
建立索引
 ↓
用户提问
 ↓
检索相关片段
 ↓
把片段交给大模型生成答案
```
在你的项目里，RAG 主要用于：

- 售后政策问答

- 商品说明问答

- 用户上传文档问答

- 图片分析结果入库后的后续问答

#### 面试里可以说：

RAG 模块主要解决客服知识库问答问题。它让系统基于上传的业务文档回答，而不是只依赖大模型自己的通用知识。

### 6. Memory 模块在哪里？

Memory 模块负责“让系统记住上下文和用户状态”。

比如：

用户第一轮说：

帮我查订单 10001

系统查完之后，会把 10001 记为最近订单。

用户第二轮说：

那帮我申请退货

这时候用户没有说订单号，但系统可以从 Memory 里拿到最近订单号，知道“那”指的是 10001。

你的项目里的记忆可以分成三类：

- 短期对话记忆：最近几轮对话内容

- 实体记忆：订单号、售后单号、用户最近关注的商品等

- 长期结构化记忆：已经创建的售后单、用户偏好、历史业务状态等

#### 面试里可以说：

Memory 模块主要解决多轮对话中的上下文连续性问题，让用户不用每句话都重复订单号或背景信息。

### 7. 数据库存储什么？

数据库不是用来存大模型的，它主要存业务数据和系统状态。

你的项目里数据库主要存：

用户信息

订单信息

订单明细

售后单

邮件发送记录或通知记录

对话记录

用户记忆

知识库文档信息

文档 chunk 信息

图片分析结果或入库后的知识内容

你可以理解为：

数据库存储的是客服业务系统需要长期保存的数据。

比如订单状态不能只存在模型上下文里，否则服务重启就没了，也没法在页面上稳定展示。

### 8. LLM 调用在哪里发生？

LLM 调用主要发生在两类地方。

#### 第一类是客服 Agent 回复生成：
```text
用户问题 + 记忆 + 工具结果
 ↓
DeepSeek
 ↓
生成客服回复
```

比如系统查到了订单状态是“已发货”，然后让 DeepSeek 组织成自然、礼貌的客服回复。

#### 第二类是 RAG 文档问答：
```text
用户问题 + 检索到的文档片段
 ↓
DeepSeek
 ↓
生成基于文档的回答
```
此外，图片理解不是 DeepSeek，而是调用智谱 GLM-5V：
```text
图片 + 用户问题
 ↓
智谱视觉模型
 ↓
图片分析结果
```
面试里可以说：

文本生成主要走 DeepSeek API，图片理解走智谱视觉模型。后端会把业务数据、记忆或检索结果组织成上下文，再交给模型生成最终回答。

### 整体流程图

你可以这样理解整个系统：
```text
用户输入
 ↓
前端发送请求
 ↓
FastAPI 后端接收
 ↓
LangGraph Agent 启动
 ↓
读取用户记忆和历史上下文
 ↓
识别用户意图
 ↓
判断下一步动作
 ↓
查订单 / 创建售后 / 读取知识库 / 图片理解
 ↓
得到业务结果或检索结果
 ↓
调用 LLM 生成自然语言回复
 ↓
更新记忆和业务状态
 ↓
后端返回结果
 ↓
前端展示回复、订单、售后单、记忆状态

再换成更接近面试白板表达的版本：
```text
用户输入
 ↓
意图识别
 ↓
Agent 决策
 ↓
工具调用 / RAG 检索 / 记忆读取
 ↓
LLM 生成回复
 ↓
结果返回
```
#### Agent 决策

Agent 判断应该怎么处理这个意图。

比如：

- 如果用户说了订单号，就直接查订单

- 如果用户没说订单号，就尝试从记忆里找最近订单

- 如果记忆里也没有，就追问用户订单号

- 如果用户要退货，还要判断是否有退货原因

Agent 的价值就在这里：它不是简单回复，而是会做流程判断。

#### 工具调用 / RAG 检索 / 记忆读取

这一步是真正干活。

- 如果是订单问题，就查订单数据库。

- 如果是退货问题，就创建售后单。

- 如果是政策问题，就走 RAG 检索文档。

- 如果是上下文缺失，就读取记忆补全。

- 如果是图片问题，就调用视觉模型。

### 如果果面试官问：你的系统整体架构是怎样的？

你可以这样回答：

这个项目整体分成前端、后端、Agent、数据库、RAG 和模型服务几部分。前端负责用户交互和结果展示，比如聊天、订单列表、售后单、文档问答和图片上传。后端用 FastAPI 提供接口，负责接收请求、调用 Agent、访问数据库和调用模型。

Agent 是核心业务决策层，我用 LangGraph 把客服流程拆成多个节点，比如读取记忆、识别意图、补全参数、执行业务操作、更新记忆和生成回复。对于订单和售后类问题，系统会查询数据库或创建售后单；对于政策类问题，会走 RAG 从上传文档里检索相关内容；对于图片问题，会调用视觉模型分析图片。

最后，系统会把业务结果、记忆上下文或检索片段交给大模型生成自然语言回复，再返回给前端展示。


你现在要记住一句核心：

前端负责展示，后端负责接口和数据，Agent 负责决策，LangGraph 负责流程编排，RAG 负责文档知识，Memory 负责上下文，LLM 负责生成自然语言。
