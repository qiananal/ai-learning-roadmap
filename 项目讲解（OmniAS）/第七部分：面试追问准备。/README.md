## 第七部分：面试追问准备。
这一部分最实用。你要把它当成面试问答稿来练。重点不是背得多，而是回答时有结构：

1. 先说原因
2. 再结合项目
3. 最后补一句优化方向

### 问题 1：为什么不用普通 Chain，而用 LangGraph？

面试官考察点:面试官想看你是不是真的理解 Agent 流程，而不是为了简历硬堆 LangGraph。

回答模板

普通 Chain 更适合线性的问答流程，比如输入问题、拼 prompt、调用模型、输出答案。但我的客服场景不是单纯线性流程，它有状态、有分支，还需要根据用户信息是否完整决定下一步。

比如用户说“那帮我退货”，系统要先读取记忆，判断“那”指哪个订单；如果缺少退货原因，就要追问；如果信息完整，就创建售后单；处理完还要更新记忆。这个流程用普通 Chain 写会比较绕。

所以我用 LangGraph 把流程拆成读取记忆、识别意图、准备动作、执行业务操作、更新记忆、生成回复几个节点。这样每一步职责清楚，也方便调试和扩展。

你要强调：不是为了用 LangGraph 而用，而是因为客服流程有状态、有分支、需要可控。

### 问题 2：RAG 为什么使用 FAISS + BM25？

面试官考察点：面试官想看你是否理解向量检索和关键词检索的区别。

回答模板

因为客服知识库里既有自然语言问题，也有很多精确信息，比如订单号、商品型号、政策名称、时间规则。单纯向量检索能处理语义相似，但对数字、型号和专有词不一定稳定。

所以我做了混合检索。FAISS 负责语义召回，比如用户换一种说法问“退款多久到账”，也能找到“3-5 个工作日原路退回”的片段。BM25 负责关键词召回，比如型号、政策名、编号这种精确匹配。

最后把两边结果做分数归一化和加权融合，提高召回稳定性。

你要强调：
```text
FAISS：按语义找
BM25：按关键词找
混合检索：更稳定
```

### 问题 3：如何降低大模型幻觉？
面试官考察点：面试官想看你是否有工程上的可靠性意识。

回答模板
我主要从三个层面降低幻觉。

第一，在业务操作上，不让模型凭空回答订单状态，而是先查数据库，拿到真实订单或售后结果，再让模型组织语言。

第二，在文档问答上，先通过 RAG 检索相关文档片段，并要求模型只基于片段回答；如果片段不足，就明确说明不确定。

第三，在页面上展示工具执行结果和文档来源片段，方便用户核查。

后续如果做生产级优化，我还会增加回答置信度、引用校验和敏感业务操作的二次确认。

你要强调
```text
实业务数据
检索片段约束
来源可追溯
重要操作二次确认
```
### 问题 4：Memory 是如何设计的？
面试官考察点:面试官想看你是否理解多轮对话，不只是把聊天历史塞进 prompt。

回答模板

我把 Memory 分成三层。第一层是短期对话记忆，保存当前会话最近几轮消息，解决上下文连续性问题。第二层是实体记忆，保存订单号、待处理售后订单号这类关键字段，用来补全后续对话里的参数。第三层是长期结构化记忆，保存售后单号、售后摘要等跨会话业务状态。

比如用户先说“帮我查订单 10001”，系统查完后会把 last_order_no=10001 写入实体记忆。下一轮用户说“那帮我退货”，系统可以直接从记忆中取出订单号，而不是让用户重复输入。

这样设计比单纯保存聊天记录更可控，因为关键业务信息是结构化存储的。

你要强调
```text
短期记忆：上下文
实体记忆：参数补全
长期记忆：业务状态
结构化存储更可控
```
### 问题 5：Agent 如何避免错误调用业务能力？
面试官考察点:面试官想看你是否考虑了 Agent 乱调用、误调用的问题。

回答模板

我没有让模型直接自由调用业务操作，而是做了几层控制。

第一，意图识别结果会被结构化成固定字段，比如 intent、order_no、reason、tool_name。

第二，在真正执行前，会有 prepare_action 节点检查参数是否完整。比如创建退货申请必须有订单号和退货原因，缺少任何一个都会先追问用户。

第三，业务能力本身也封装在后端函数里，Agent 只能调用允许的几个动作，比如查订单、创建售后、发送邮件。

这样可以避免模型在信息不足时直接操作业务数据。

你要强调
```text
结构化 decision
参数校验
信息不足追问
工具白名单
```
### 问题 6：如果用户量增加，系统如何优化？
面试官考察点:面试官想看你有没有从 Demo 思维扩展到工程思维。

回答模板

如果用户量增加，我会从几个方面优化。

第一，数据库从 SQLite 切换到 MySQL 或 PostgreSQL，支持更好的并发和数据管理。

第二，RAG 索引从本地 FAISS 文件升级到独立向量数据库，比如 Milvus、Qdrant 或 Chroma，方便多用户索引管理和扩展。

第三，模型调用层增加缓存和限流，比如相同知识库问题可以做语义缓存，避免重复调用模型。

第四，耗时任务异步化，比如文档上传后的解析和向量化可以放到后台任务队列。

第五，增加日志监控和错误追踪，方便定位 Agent 失败、检索失败或模型调用失败的问题。

你要强调
```text
数据库升级
向量库升级
缓存限流
异步任务
日志监控
```
### 问题 7：为什么要把业务动作封装出来，而不是让大模型直接生成 SQL？
面试官考察点:看你有没有安全意识和工程边界意识。

回答模板

我没有让大模型直接生成 SQL，因为客服业务涉及订单、售后、用户数据，如果让模型直接操作数据库，风险比较高，也不好控制权限。

我的做法是把业务动作封装成固定后端函数，比如查订单、创建售后、发送邮件。Agent 只能在这些受控能力里选择，并且入参要通过结构化 schema 校验。

这样做的好处是安全边界更清楚，业务逻辑也更稳定。

### 问题 8：RAG 检索不到内容怎么办？
面试官考察点:看你是否考虑失败路径。

回答模板

如果检索不到相关文档片段，系统不会强行编答案，而是提示当前知识库没有可用内容，建议先上传相关文档。

如果检索到了片段但内容不足，prompt 里会要求模型明确说“不确定”，而不是泛泛回答。

后续可以优化为低置信度二次检索，比如扩大 top_k、改写用户问题、或者切换关键词检索权重。

### 问题 9：为什么图片理解结果也能进入知识库？

面试官考察点:看你是否理解多模态和 RAG 的结合方式。

回答模板

图片本身不能直接进入文本 RAG，所以我先用视觉模型把图片转成文字分析结果，比如商品外观、破损情况、截图中的关键信息。然后把这段分析结果作为文本写入知识库。

这样后续用户可以基于图片分析结果继续问答，比如“刚才那张图片里商品有什么问题”。本质上是把多模态信息转换成可检索的文本知识。

### 问题 10：这个项目目前有什么不足？

面试官考察点:看你是否诚实、是否知道下一步怎么优化。

回答模板

目前这个项目更偏向本地演示和简历项目，还不是生产级系统。主要不足有几个。

第一，数据库默认使用 SQLite，适合 Demo，但高并发下需要换成 MySQL 或 PostgreSQL。

第二，RAG 目前是基础版本，chunk 切分还是固定长度，没有做更复杂的版面解析、表格解析和重排模型。

第三，Agent 的业务能力还比较少，目前主要是查订单、创建售后、发送邮件，后续可以扩展更多真实客服操作。

第四，缺少完整的权限、安全审计和人工客服接管机制。

不过这个版本已经覆盖了 AI 应用开发里比较核心的链路，包括 Agent 流程、记忆、业务数据调用、RAG、图片理解和前端可视化。

这个回答很重要。不要假装项目完美，面试官一追就露馅。承认不足，但要告诉他你知道怎么改。

### 问题 11：你在这个项目里主要做了什么？

面试官考察点:看你是不是只包装项目，还是能讲清楚个人贡献。

回答模板

我主要完成了四块工作。

第一是客服 Agent 主流程，把用户输入、意图识别、参数补全、业务操作、记忆更新和回复生成串起来。

第二是记忆系统，支持短期对话记忆、实体记忆和长期结构化记忆，让系统能处理多轮客服问题。

第三是知识库问答，完成了文档上传、解析、切分、向量化、FAISS 和 BM25 混合检索，以及基于来源片段的回答生成。

第四是多模态能力和演示页面，接入图片理解接口，并把订单、售后、记忆、RAG 来源和图片分析结果可视化展示出来。

### 问题 12：这个项目和普通客服机器人有什么区别？

面试官考察点:看你是否能讲项目价值。

回答模板

普通客服机器人更多是 FAQ 问答或者单轮聊天，而这个项目更强调业务闭环。

它不仅能回答问题，还能根据用户意图查询订单、创建售后单，并且会记住最近订单和售后状态。对于政策类问题，它可以基于上传文档回答；对于图片类问题，它可以调用视觉模型分析。

所以它不是单纯聊天机器人，而是一个结合业务数据、记忆、知识库和图片理解的客服 Agent Demo。

### 90 秒项目介绍

你可以直接背这一版：

我做的是一个面向电商售后场景的多模态 AI 客服 Agent 系统。它主要解决传统客服在处理订单查询、退换货、售后政策咨询时，需要反复查订单、看历史对话和查文档，效率比较低的问题。

系统前端提供一个客服工作台，用户可以直接聊天，也可以查看订单、售后单、记忆状态，还可以上传文档和图片。后端用 FastAPI 提供接口，核心 Agent 流程用 LangGraph 实现。我把一次客服请求拆成读取记忆、识别意图、参数补全、执行业务操作、更新记忆和生成回复几个步骤。

比如用户先说“帮我查订单 10001”，系统会查询数据库返回订单状态，并把这个订单号写入记忆。下一轮用户说“那帮我退货”，系统可以从记忆里自动补全订单号，然后继续追问退货原因或创建售后单。

除了客服 Agent，我还实现了文档问答和图片理解。文档上传后会被解析、切分成 chunk，然后通过 sentence-transformers 生成向量，并结合 FAISS 语义检索和 BM25 关键词检索做混合召回，最后让 DeepSeek 基于检索片段回答。图片理解部分接入了智谱视觉模型，图片分析结果也可以写入知识库，支持后续检索问答。
这个项目的重点不是单纯聊天，而是把 Agent 流程、业务数据、记忆系统、RAG 知识库和多模态能力串成一个完整的 AI 应用闭环。
