# 核心概念：Git 的“三个小房间”
在开始动手前，需要知道，Git 存一个档，其实要把数据挪过三个不同的“小房间”。

工作区（Working Directory）： 就是你现在肉眼看到的、正在写代码的文件夹。你在这里增删文件，Git 都看着呢，但它还没帮你保存。

暂存区（Staging Area）： 相当于你的“临时购物车”。你觉得哪几个文件写得差不多了，准备存个档，就先把它放进购物车里。

本地仓库（Repository）： 相当于你的“正式游戏存档”。一旦你确认把购物车里的东西结算，Git 就会把它变成一个永久的、带有编号的“历史存档”。

# 动手实战：完成你的第一个正确存档

## 第一步：开启存档功能（初始化）

我们要告诉 Git：“从现在开始，你要帮我盯着这个文件夹了！”

在终端输入：
```Plaintext
git init
```
执行完后，你的文件夹里会多出一个看不见的 .git 文件夹（这就是它的内部存档数据库）。

## 第二步：把文件放进“购物车”（暂存）

假设你在这个文件夹里新建了一个 README.md 文件（或者修改了某个文件），你想把它的状态存下来。

在终端输入：
```Plaintext
git add README.md
```
如果你修改了很多文件，懒得一个一个加，可以输入 
```Plaintext
git add .
```
（注意后面有个点），意思是把当前文件夹下所有修改过的东西全部塞进购物车。

## 第三步：正式“敲下图章”存个档（提交）

现在购物车里有东西了，我们要正式生成一个存档了。

在终端输入：
```Plaintext
git commit -m "我的第一次正确存档"
```
通俗解释： -m 后面双引号里的字，就是你给这个存档起的**“备注名”**。一定要写人类能看懂的话，比如“修复了第10行的Bug”或者“完成了草莓分类的界面”。这样以后你坐时光机回来的时候，才知道这一站发生了什么。


## 要把你本地的存档“同步/上传”到 GitHub 官网上，我们还需要完成两个动作：“拉一条网线（关联远端）” 和 “把货运过去（推送）”。

## 第一步：把本地文件夹和 GitHub 的网址“拉一条网线”

既然我们之前删除了旧的配置，现在需要重新告诉 Git 你的云端仓库在哪。

打开你的 GitHub 网页，找到你的仓库。

复制它绿色的 Code 按钮下的 HTTPS 链接（长得像 https://github.com/...）。

在 VS Code 终端里输入下面这行命令（把后面的网址换成你刚刚复制的）：

```Plaintext
git remote add origin https://github.com/你的用户名/ai-learning-roadmap.git
```
白话翻译： remote 是远程的意思，add 是添加。这句话的意思是：“Git 你听好，我给我的云端仓库取名叫 origin（源头），它的网线地址是后面这串 URL。”

## 第二步：把你的本地存档“推”上云端

网线接好后，我们要执行最关键的一步——送货上门。
```Plaintext
在终端里输入：git push -u origin main
```
💡 注意： 如果你的 GitHub 仓库默认主分支叫 master，请把命令最后的 main 改成 master。如果不确定，可以先看看你网页上显示的是 main 还是 master。


如果云端上有新东西，而本地电脑上没有。

解决办法：先把云端的东西接过来，再一起推上去

把云端的文件拉取下来

在终端输入这行命令（注意，因为刚才起名字时用了 ai-learning-roadmap 代替了默认的 origin，所以我们跟着你的名字走）：
```Plaintext
git pull ai-learning-roadmap main --allow-unrelated-histories
```
再推上去。

## 挑战一：学会写游戏“隔离带”—— .gitignore（下一次写代码前必学）

1. 为什么要学？
目前的文件夹叫 ai-learning-roadmap。如果以后在里面跑 Python 代码、训练深度学习模型，系统会自动生成一堆类似 __pycache__（缓存）、runs/（训练日志）或者 .pth（几百 MB 的权重文件）。

如果把这些垃圾和庞然大物一股脑推送到 GitHub，你的云端仓库瞬间就会卡死、崩溃。

2. 怎么学？

在你的文件夹根目录下，新建一个普通文件，名字精准地叫做：
```Plaintext
.gitignore
(注意有个点)
```
你在里面写上什么名字，Git 就会彻底假装看不见什么文件。比如在里面写下：
```Plaintext
__pycache__/
*.pth
*.onnx
.env
```
在工业界，我们永远会把 .gitignore 放在最外层的项目根目录下

白话翻译：“Git，以后只要是缓存文件夹、只要是后缀为 .pth 和 .onnx 的模型权重、以及我的私人密钥文件 .env，你统统装作看不见，不许把它们放进购物车！”

### 如果已经不小心上传上去了怎么办？

不小心把大文件/密码传上去了怎么办？

 * 答： 先在 .gitignore 里写好规则，然后用 git rm --cached 把大文件从 Git 追踪里抠出来，再重新 commit 提交。


把已经传上去的 .pth 文件从 Git 的掌心里“抠出来”。

在 VS Code 终端里输入这行命令（注意 --cached 意思是只从 Git 仓库的购物车/云端里删掉，不会删掉本地电脑里的真实文件，非常安全）：

```Bash
git rm --cached git/demo.pth


(如果你的路径有变，把后面的路径改成你本地对应的相对路径)
```
## 挑战二：游戏里的“多结局平行宇宙”—— 分支（Branch）

1. 为什么要学？

你现在所有的操作都在一条叫 main 的主线上。

在工业界，main 线上跑的都是正在运行的完美代码。如果你想尝试一个新想法（比如：把你的草莓识别模型从 YOLOv5 升级到 YOLOv8），你绝对不能直接在 main 上改。万一改到一半改崩了，原本能运行的代码也瘫痪了。

这时候，你需要拉出一个“平行宇宙（分支）”，在里面随便折腾，折腾好了再合并回主线；折腾坏了直接把这个平行宇宙删掉，主线毫发无损。

1. 核心命令：
```bash
git checkout -b feature/yolov8：复制当前主线，切出一个叫 “yolov8” 的平行宇宙。
```
-b 就是 branch（分支）。这行命令相当于在游戏里说：“以现在的进度为基础，复制一个叫 strawberry-doc 的平行宇宙，并且我的肉身立刻穿越进去！”

### 怎么推送分支到云端：

直接 git push 

会报错：fatal: The current branch feature/yolov8 has no upstream branch.（致命错误：当前的平行宇宙在云端没有对应的接收人。）

正确的做法是：

你要告诉云端，你要在云端也建一个一模一样的平行宇宙。命令是：

```Bash
git push -u ai-learning-roadmap feature/yolov8
```

在 VS Code 本地确认你在哪个分支：
在终端输入：

```Bash
git branch
```
它会列出你本地所有的分支，并且前面带星号（*）且显示为绿色的那一行，就是你当前肉身所在的分支。

怎么切换分支：
```bash
git checkout main：一键穿越，回到安全的主线上。

```

## 挑战三：多人联机时的“防追尾”—— 冲突解决（Conflict）

1. 为什么要学？

这就是你刚才遇到的 rejected 报错的升级版。

在团队里，你和你的同事小明同时下载了第 10 版的代码。你们俩同时修改了 main里面的demo.md 的第 5 行。
小明下午 2 点把他的修改推上了 GitHub。你下午 3 点去推的时候，Git 就会报警：“停！第 5 行被小明改了，你现在也改了第 5 行，我不知道该听谁的，你们俩打一架吧！”

这时候，代码就会出现冲突（Conflict）。你需要学会如何在 VS Code 里，肉眼对比你和小明的代码，手动选择“保留你的”、“保留小明的”还是“两个都留”。

### 工业界最标准、最安全的解冲突手法只有三步，我们今天直接把它通关：

1. 把主线 main 的最新代码抓到你的分支里

为什么要抓在分支里？：

   - 保护主线（线上环境）的绝对安全
在工业界，main 分支里的代码随时可能被自动打包部署到生产环境（比如正在运行的草莓质检机器）。
如果你直接在 main 上解冲突，在你肉眼找 Bug、跟同事扯皮的这十分钟里，主线代码是处于“破损、冲突、无法运行”的状态的。万一这时候系统自动抓取了代码，线上的机器直接就瘫痪了。
   - “谁提出来的，谁在私底下解决”。Git 的原则是：主线永远是对的，错的是落后的人。

确保你现在在 feature/yolov8 分支，输入：
```Bash
git pull ai-learning-roadmap main
```
1. 睁大眼睛，在 VS Code 里“肉眼排雷”
执行完上一命令后，你的 demo.md 文件会瞬间变成“彩色”的。VS Code 会非常智能地用红蓝颜色把冲突的地方框起来。

1. 和同事协商后，重新提交。
2. 
排雷完毕，保存文件。最后用你的肌肉记忆三连招，把干净的代码再次推上去：

```Bash
git add .
git commit -m "fix: 解决与 main 的文档冲突"
git push
```
这时候你再去刷新 GitHub 的 PR 页面，红色的警告就会瞬间变成绿色的“可安全合并”！



## 🏁 Git 部分的最终“闭卷复习”

### 在把 Git 翻篇之前，你只需要在脑子里死死记住这 3 个核心心法，面试时不管是单选还是场景问答，你都能闭着眼睛答对：

### “三个房间”心法： add 是放进临时购物车，commit 是打包成正式本地存档，push 才是联网送到 GitHub。

### “安全隔离”心法： 大的模型权重（.pth）、大量的数据集、私密的 API 密钥，永远要在第一天就写进 .gitignore，绝对不能传上云端。

### “协作闭环”心法： 实习生永远不在 main 上写代码。拉新分支开发 ->推送分支 ->提 PR ->冲突了就在本地分支 pull main -> 手动三选一解冲突 ->重新 push。
